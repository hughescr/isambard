# Isambard Architecture

Isambard is a self-improving agentic thought partner built on the Claude Agent SDK, TypeScript, and Bun. It follows a layered architecture with a single composition root (`src/app/`) that wires subsystems together; all external I/O goes through platform integrations that map at the boundary into platform-agnostic agent types. The runtime working directory is `scratch/`, which is a separate live git repo — production code lives only in `src/`.

## Module Map

| Module | Responsibility | Layer |
|---|---|---|
| `src/utils/` | Pure utilities: time, text, filename, path security, retry, media processing. No domain knowledge. | Foundation |
| `src/errors/` | Centralized error hierarchy (`IsambardError` base, `StorageError` and `DiscordError` subtrees, `ErrorCode` enum). | Foundation |
| `src/config/` | Zod-validated configuration loading from environment variables. | Foundation |
| `src/storage/` | DynamoDB client, repository base, memory tool subsystem, contacts, person allowlist, task session persistence. | Data |
| `src/services/` | Resilience infrastructure: health registry, reconnection loop, lifecycle orchestrator, outbox, approval saga, allowlist saga. | Infrastructure |
| `src/agent/` | Platform-agnostic Claude agent: MCP servers, perch scheduler, answer classifier, question registry, stream tracker, context builder, history providers. | Agent |
| `src/integrations/discord/` | Discord bot: channel registry, inbox, catch-up, ledger-composed presence, live task-board embeds, message history, attachments, slash commands. | Integration |
| `src/integrations/email/` | WildDuck HTTP API client with SSE push, outbound approval workflow, rate limiter. | Integration |
| `src/integrations/bsky/` | AT Protocol client: feeds, posts, DMs, social graph, checkpoint tracking, rejection backend. | Integration |
| `src/integrations/caldav/` | CalDAV client (tsdav), per-user credential registry, calendar slash commands. | Integration |
| `src/app/` | Composition root: factory functions that wire all subsystems together. | Composition |

## Layering

Import direction runs strictly from higher layers toward lower ones. The enforced dependency order, from most independent to most dependent:

```
utils  →  errors  →  config  →  storage
                              →  services  →  storage
                                           →  agent  →  storage, services, email, bsky, caldav
                                                     →  discord  →  agent, email, bsky, caldav, storage, services
                                                                 →  app  (composition root, imports everything)
```

The composition root (`src/app/`) is the only module allowed to import from all layers simultaneously. It contains six factory functions: `createStorageLayer`, `createDiscordInfrastructure`, `createContextLayer`, `createMCPServers`, `createCatchUpSignalAdapter`, and `loadIdentityContext`. These construct subsystems and inject their dependencies rather than letting subsystems find each other.

Platform integrations (Discord, Email, Bluesky) each own their own setup concerns. Discord is the hub for approval UI (buttons, modals) and routes approvals back to email and Bluesky outbound handlers. CalDAV is independent of the agent module — it provides data but does not call agent APIs.

`src/agent/` does not import from `src/integrations/discord/`. The Discord integration calls into the agent, never the reverse. Boundary mapping — translating Discord-specific types to the agent's `MessageContext`/`PlatformImage` — happens in `src/integrations/discord/setup/coordinator-setup.ts`.

## Module Boundaries

Boundaries are enforced by two complementary mechanisms.

**`eslint-plugin-boundaries`** (`eslint-boundaries.config.mjs`) implements the layering table above as a lint rule with `default: 'disallow'`. Every allowed import direction is an explicit rule; anything not listed is an error. The same config also enforces entry-point discipline: production code crossing a module boundary must import from the barrel (`index.ts`), not from internal files. This is the `!index.ts` catch-all disallow rule.

**`@hughescr/eslint-plugin-module-boundaries`** adds three finer-grained rules:
- `no-internal-in-barrel` — barrel `index.ts` files must not re-export symbols tagged `@internal`.
- `no-cross-module-internal` — production code must not import an `@internal`-tagged symbol from a different architectural module.
- `no-star-export-from-non-barrel` — barrel files must not `export *` from a non-barrel source file (star-exports from another `index.ts` are allowed).

**`@internal` JSDoc tags** mark symbols that are implementation details — exported for intra-module use (e.g., sub-directory to parent directory), but not part of the public cross-module API.

**Barrel export policy**: each `index.ts` conservatively exports only what other modules actually need. Over-exporting is caught by `bun dead-code` (knip). Tests may bypass the barrel and import directly from source files to access internals without inflating the public API surface.

## Data Layer

All persistent state lives in a **single DynamoDB table** with PK/SK primary key and two GSIs:

- **GSI1** (`GSI1PK` / `GSI1SK`): layer-and-time index, used for memory layer queries and time-range scans.
- **GSI2** (shared partition space): multiple unrelated subsystems share this GSI using non-overlapping partition key prefixes. Known GSI2 partitions:
  - Channel registry items — partitioned by guild ID.
  - Tag index items — partitioned as `TAG#<tagname>`.
  - Contact lookup rows — partitioned as `CONTACT_LOOKUPS`.

**Memory tool** (`src/storage/memory-tool/`) implements a three-layer memory architecture exposed to the agent via MCP:
- `/identity/` — Long-lived self-knowledge, no TTL, auto-loaded every session.
- `/state/` — Working state, no TTL, selectively auto-loaded via sigmoid scoring.
- `/events/` — Time-stamped event log, TTL-based expiry, not auto-loaded.
- `/users/{userId}/` — Per-user memory, keyed by person ID.

Auto-loading of `/state/` items uses `sigmoidScore()`, which combines access frequency (sigmoid activation) and recency (exponential decay) to prioritize what gets injected into context. The tag index uses per-tag atomic counters (`META_COUNT`) and fat-pointer items that carry content preview data, avoiding a centralized registry and the race conditions that come with it. A three-phase background reconciler keeps the tag index consistent.

**Contacts** (`src/storage/contacts/`) provide a cross-platform address book. Each contact record holds a set of platform identifiers (Discord user ID, email address, Bluesky handle, etc.). The CONTACT_LOOKUP GSI enables identifier-to-contact resolution without a full scan. A two-phase reconciler handles orphan cleanup and missing-lookup repair.

**Person allowlist** (`src/storage/person-allowlist.ts`) gates outbound writes (email sends, Bluesky posts/DMs) by person ID rather than per-platform raw addresses. A reverse-map resolves any known identifier to its person ID for allowlist checks.

**Session journal** (`src/storage/session-journal/`, long-lived conductor sessions only): every observable session-lifecycle fact — envelope submission, turn completion, delivery, background-task start/completion/loss, compaction, session open/close — is written through to its own `SESSION_JOURNAL#<role>` partition, one role (`conversation` or `perch`) per partition, deliberately outside `/events` and carrying no GSI1 keys so these rows never enter the memory tool's tag index, embedder queue, or `LAYER#events` time-range scans. Crash recovery (`src/agent/session/recovery.ts`) reads a role's journal window at boot and derives which background tasks never reached a terminal state and which turns finished without a confirmed delivery, so the conductor can report the former as lost and safely redeliver the latter exactly once (guarded by an in-memory delivery guard seeded from the journal's own `response_delivered` rows). The one exception to "not memory" is the compaction summary: each compaction's PostCompact summary is logged as an ordinary tagged memory row at `/events/compaction/<timestamp>`, deliberately Izzy-visible like any other event. The SDK's per-session transcript files (`~/.claude/projects/<project>/`) are always pruned by age (`session.transcriptRetentionMs`, default 7 days) rather than wiped on every startup, sparing whichever of the two role-keyed session ids are still resumable — the one-shot path's unconditional startup wipe was removed in P13b along with the mode flag.

## Agent Subsystem

The agent module is **platform-agnostic**. It receives `MessageContext` objects (text, optional `PlatformImage` attachments) and emits stream events — it has no knowledge of Discord, email, or Bluesky at the type level.

The agent exposes its capabilities to Claude through a suite of **custom MCP servers**: memory (view, store, search, log), Discord message history, email (inbox, send, archive, reply, drafts), Bluesky (feeds, posts, DMs, social graph, rejection management), Discord inbox (unread overview, channel summary), CalDAV (calendar events), contacts (lookup, search, create, update, delete), media processing (video analysis, spectrograms), Wikipedia, user context, and health (read-only per-service status, deliberately reachable during an outage).

Supporting machinery within the agent module:
- **Context builder**: assembles the per-turn user message prefix by loading auto-load memory items, perch context (email inbox state, Bluesky DM notifications, rejected posts), and calendar events.
- **AnswerClassifier**: LLM-based (Haiku) classifier that determines whether an incoming message is an answer to a pending question, an interruption, or an unrelated message.
- **QuestionRegistry**: tracks pending questions with timeouts; routes button-interaction answers back to the waiting handler.
- **StreamTracker**: accumulates a stream's latest thinking/text/pending-tool-use and the session id captured from `system/init`, so an interrupted turn's partial work can be captured (`conductor.ts` instantiates one per turn). It does not itself decide anything about resumption — a background task that never reaches a terminal state is detected at boot from the role's session journal (see "Session journal" above), not by StreamTracker or any per-turn auto-resume.
- **EventDeltaTracker**: surfaces only new events between interactions, avoiding re-injection of already-seen context.
- **PersonHistoryCoordinator**: aggregates cross-platform message history from Discord, Email, and Bluesky providers, keyed by contact person ID.

**Perch system** (`src/agent/perch/`) provides time-based autonomous activity scheduling. A cron-based scheduler (`scheduler.ts`) uses jitter (cron-parser H option) to trigger perch slots at graduated suggestion levels depending on the hour; each trigger calls `createPerchDriver`'s `runSlot()`, which submits the slot as a turn on perch's own long-lived conductor session (design doc section 6/9 — there is no separate one-shot perch "session runner"). Deferral against an already-running slot is the driver's job, not a bot-wide mode machine: a trigger that fires mid-slot just sets a pending flag, resolved to whatever slot the clock says it is once the running turn settles. Near the end of a slot the driver submits a `[WRAP-UP]` envelope at the highest submit priority so it runs as the conductor's very next turn; past a grace period after that it interrupts an overrunning turn via `conductor.interruptCurrent()`. A perch-channel Discord message arriving mid-slot is not suspended/resumed against a separate session — `handlers.ts` submits it as an ordinary turn on the same perch conductor, queued behind whatever is already running (see `src/agent/perch/README.md`).

**Agent / skill / plugin definitions** live outside `src/` in `agents-skills-plugins/` (subagent `.md` files, skill directories with `SKILL.md`, and `plugins.json` for marketplace plugins). These are content artifacts, not code. At startup, `src/agent/skill-agent-loader.ts` copies them into `scratch/.claude/agents/` and `scratch/.claude/skills/` so the Claude Agent SDK's auto-discovery picks them up from the runtime working directory.

## Platform Integrations

Each integration in `src/integrations/` owns its full vertical slice: types, errors, client, history provider, and any approval or saga machinery it needs.

**Discord** is the primary operator interface. The bot is a thin orchestrator (`bot.ts`) that delegates to setup modules in `src/integrations/discord/setup/`. There is no bot-wide operational-mode state machine (the `state/` directory and its `BotStateManager` were retired once the conductor model landed) — instead, presence is *composed*, on every tick, from the two session ledgers themselves (`presence/presence-view.ts`'s `composePresence`): which of `conversation`/`perch` currently has an open turn, task/workflow/monitor counts from `Ledger.tasks`, and a compacting marker, rendered to a Discord custom-status string and throttled by a shared `PresenceThrottle` (design doc section 8). `presence/manager.ts` applies that composed view; there is no subscribe-to-mode-transitions step, no explicit idle bootstrap (the very first compose, before either ledger has emitted an event, already renders idle), and no separate presence path for "catching up" — a startup catch-up run is just turns on the conversation conductor. (Tool and MCP server selection is not mode-driven; the inbox server is attached to every turn.) The channel registry is DynamoDB-backed with write-through cache and supports well-known channels (`general`, `catch-up`, `perch-time`, `fallback`). The inbox system tracks unread messages with checkpoint persistence; a startup catch-up turn drains the backlog through the conversation conductor rather than a separate catch-up session.

The **task board** (`presence`'s sibling, `src/integrations/discord/task-board/`) is composed from the same ledgers: `LedgerTask` now tracks every non-ambient sub-agent, workflow and background shell command (foreground sub-agents included, ended by their `tool_result`), with the latest `task_progress` usage, the SDK's AI progress summary, and a workflow's parsed `workflow_progress` (phases and per-agent state), and finished tasks linger in `Ledger.finishedTasks`. `composeTaskBoards` groups tasks by launching channel and turn; `renderTaskBoardEmbed` is a pure renderer to a Discord embed (ten-cell meter, tokens, elapsed, kind emoji shared with presence); `TaskBoardManager` posts one embed per board and edits it through a trailing-edge throttle (`discord.taskBoard.editIntervalMs`), with a final edit on completion and never again. Design: `docs/plans/task-board.md`.

**Email** uses the WildDuck HTTP API for all operations (read, search, send, flag management, draft upload). SSE push with poll fallback drives real-time inbox notifications. Outbound sends require admin approval via Discord unless the recipient is on the person allowlist. A token-bucket rate limiter (capacity 24, refill 1/hr) prevents send storms. Custom keyword flags use no `\\` prefix — WildDuck HTTP convention, not IMAP.

**Bluesky** wraps `@atproto/api`'s `AtpAgent`. MCP tools expose handles everywhere; DIDs are internal. Outbound replies and DMs flow through an approval workflow with Discord buttons/modals. Admin rejections are persisted to a `BskyRejectionBackend` (DynamoDB, 30-day TTL) and surfaced back to the agent in perch context so it can retry or acknowledge them. Feed and notification consumption is idempotent via a checkpoint manager backed by the memory tool.

**CalDAV** stores per-user credentials in DynamoDB (no global SST secrets). Discord `/calendar` slash commands manage credentials. The agent accesses calendar data through the `caldav-mcp-server` MCP tool; CalDAV itself does not import from the agent module.

Boundary mapping between Discord-specific types and the agent's platform-agnostic types happens in `src/integrations/discord/setup/coordinator-setup.ts`. The other platform setups (`email-setup.ts`, `bsky-setup.ts`, etc.) handle their own initialization and wire approval callbacks back into the Discord approval infrastructure.

## Services Layer

`src/services/` provides resilience and workflow infrastructure:

- **HealthRegistry**: registers named services and tracks their health status for observability.
- **ReconnectionLoop**: wraps external service connections with exponential-backoff auto-reconnect.
- **LifecycleOrchestrator**: sequences startup (in dependency order) and graceful shutdown.
- **Outbox pattern** (`services/outbox/`): DynamoDB-backed reliable message delivery with a background drainer and retry, ensuring eventual delivery even across restarts.
- **ApprovalSaga** (`services/approval-saga/`): distributed approval workflow for multi-step, stateful human-in-the-loop decisions persisted in DynamoDB.
- **AllowlistSaga** (`services/allowlist-saga/`): multi-step Discord UI flow (button → modal → confirm) for adding a contact to the person allowlist, with DynamoDB state and optimistic concurrency.

## Cross-Cutting Patterns

- **Repository pattern**: all DynamoDB access goes through typed backend classes with a common base; no ad-hoc SDK calls in business logic.
- **Dependency injection**: subsystems receive their dependencies as constructor arguments or factory parameters, never via module-level singletons.
- **Zod schemas**: all external data (config, DynamoDB records, MCP tool arguments, API responses) is validated at the boundary with Zod before entering typed TypeScript.
- **Branded types**: `MemoryPath`, `LayerName`, `ChannelId`, `GuildId`, `UserId`, `MessageId` and others prevent mixing identifiers of different kinds. Factory functions (`createLayerName()`, `createContentType()`) and type guards (`isLayerName()`, `isContentType()`) replace unsafe `as` casts with runtime-validated construction.
- **Class-based components**: `EventDeltaTracker`, `AnswerClassifier`, `StreamTracker`, `QuestionRegistry`, `DiscordRateLimiter`, `PresenceManager`, `MessageCoordinator` are proper TypeScript classes with private fields.
- **Retry with exponential backoff**: `src/utils/retry/` provides generic async and async-generator retry wrappers with error classification for intelligent retry decisions. Applied to Claude API calls, DynamoDB operations, and Discord API calls.
- **Structured logging**: log entries carry correlation IDs for tracing requests across subsystem boundaries.
- **`assertNever()`**: exhaustiveness helper for discriminated union switches that throws `InvariantViolationError` at runtime if an unhandled variant slips through.
- **Lost-task recovery from the journal**: crash recovery (`src/agent/session/recovery.ts`) reads a role's session journal window at boot to find background tasks that never reached a terminal state, reporting them as lost rather than silently forgetting them — see "Session journal" above.
- **Activity auto-logging**: `ActivityLogger` records cross-platform interactions automatically for cross-platform context awareness.

## Configuration and Errors

`src/config/` loads all configuration from environment variables using the `env-var` package for type coercion, validated by Zod schemas at startup. Retry constants live in `config/retry-config.ts` and are imported by the retry utilities.

`src/errors/` defines `IsambardError` as the base class for all application errors. It carries a typed `code: ErrorCode` field and a context bag for structured diagnostics. Two main subtrees exist: `StorageError` (DynamoDB, memory tool, contacts, reconciliation errors) and `DiscordError` (channel registry, presence, permission errors). A separate `PathSecurityError` handles file path validation failures. All error codes are centralized in `ErrorCode` enum in `errors/codes.ts`.

## Session Architecture

There is no mode flag: the long-lived, journaled conversation conductor described above is the only path — `SESSION_MODE` and `session.mode` were removed from `sessionConfigSchema` (P13b) once production soaked cleanly, along with the one-shot `handleInput`-per-message agent, the perch and catch-up session runners, and their tests. `src/index.ts` unconditionally *builds* (but never opens) the conductor and hands it to `createDiscordBot`; the bot's `clientReady` handler is what actually calls `open()`, once the guild cache and channel registry exist. `open()` pushes a `shouldQuery:false` `[BOOT]` handshake envelope (the boot bundle when there is one, otherwise a bare open marker; a mid-life reopen pushes a reopen marker) onto the new session's queue before it awaits any frame: with a streaming-input prompt the SDK CLI emits nothing — not even the `system/init` frame that carries the session id — until it has read its first user message, so a silent open would never resolve (found on the first production start, 2026-09-06; the handshake yields `init` plus a bare `result` with no model turn). A perch conductor is built the same way, but only when `config.perch?.enabled` is also set — an unconfigured or disabled perch is not built at all, so a default deployment with no perch config runs the conversation conductor alone. Retention of stale session files always runs through `pruneStaleSessions`, ageing out transcripts other than the two live role-keyed sessions (conversation, perch); the one-shot path's unconditional wipe-on-startup is gone. Rollback for this package (and any change to `src/index.ts`, `src/config/schemas.ts`/`loader.ts`, or the deleted one-shot files) is a branch reset to the previous tag plus `bun run deploy:running` — there is no env var to flip back.

**Boot re-seed by kind** (R1): a `SessionStart` hook fires with one of three `BootKind`s, and `src/agent/session/boot-bundle.ts`'s `createBootBundleBuilder` renders a different section set for each — no kind repeats context already in the transcript, and no kind drops context that was never shown:

| Kind | When | Conversation role injects | Perch role injects |
|---|---|---|---|
| `fresh` | cold process start | identity, current focus/state, events (since `eventsSinceMs` when given, else the rolling `bootEventsWindowMs` window), task list, channel list, recently-talked-to users, active tasks — no lost tasks or undelivered envelopes, which are the merged Discord boot envelope's exclusive responsibility (see below), so a restart never shows the same recovery content in both places | identity, task list, the full `buildPerchContext` block, lost tasks, undelivered envelopes |
| `compact` | working memory was just reset by a `/compact` | identity, current focus/state, events since the mark, task list, active tasks — no channel list, recent users, lost tasks, or undelivered envelopes, because nothing was lost across a compaction (Discord turns are held by the conductor for its duration) | same sections as `fresh` |
| `resume` | process restart, transcript survived | only the live active-task set (from the ledger) — no identity/state/task-list/channels, since none of that was lost, and no events/lost-tasks/undelivered either (again the merged Discord boot envelope's exclusive job); `build()` returns `''` (and the hook adds no `additionalContext` at all) once even the active-task list is empty | lost tasks, undelivered, active tasks only, else `''` |

On the Discord side, the boot bundle and the inbox catch-up no longer inject as two separate messages: `runConductorInboxInit` (`src/integrations/discord/setup/catchup-setup.ts`) builds and submits ONE merged boot envelope once the crash-recovery/replay sequence resolves — the unread overview, events since a journal-derived boundary (`src/agent/session/recovery.ts`'s `lastKnownAt`, the max `at` over the conversation journal's `turn_completed`/`turn_failed` entries — deliberately NOT `turn_submitted`, which has no corresponding `JournalEntry` variant and, even if it did, a submission alone would not establish that Izzy actually saw or processed anything — falling back to `bootEventsWindowMs` when the journal has none), the recovery's lost tasks (sourced from a pre-`conductor.open()` snapshot — see `ConversationConductorResult.bootLostTasks` — so it cannot race `Conductor.open()`'s own `task_lost` journal write), and the undelivered replies this same boot actually redelivered. `ContextPolicy`'s events mark is seeded from that same boundary BEFORE `runBootSequence` opens the ingress gate (not from inside the merged-envelope builder itself, which runs after), so a live turn released by that gate can never race the seed against a stale mark. The merged envelope submits through a turn (`shouldQuery: true`) when it carries unread mail or a lost task, or is appended without opening one (`Conductor.appendWithoutTurn`) when it carries only an events/redelivered summary that does not need a reply — and submits nothing at all when there is genuinely nothing to report.

**Compaction threshold and its tuning** (Q4, Q11): `session.compactThresholdPercent` (`SESSION_COMPACT_THRESHOLD_PERCENT` env var, default 60) is the context-window usage percentage at which `CompactionGuard` (`src/agent/session/compaction-guard.ts`) submits a `/compact`. It is a live value — `CompactionGuard.setThresholdPercent`/`getThresholdPercent`, exposed on `Conductor` as `setCompactionThresholdPercent`/`getCompactionThresholdPercent` — rather than a value fixed at session construction. `src/agent/session/compaction-tuner.ts`'s `createCompactionThresholdTuner` (wired into both `createConversationConductor` and `createPerchConductor` in `src/app/sessions.ts`) subscribes to each role's `LedgerStore` and nudges this live threshold toward a configured target inter-compaction interval, derived from Q4's `CompactionTelemetry` (`compaction-telemetry.ts`) records: consecutive *finished* records' `startedAt` deltas give the observed intervals, recomputed on every `compact_boundary` `sdk_frame` event, and only the most recent `INTERVAL_HISTORY_WINDOW` (5) of them are ever considered, so a long-past burst of frequent compactions cannot keep the threshold pinned at a band edge once conditions settle. Three independently-optional env vars configure the tuner's band, all read in `src/config/loader.ts`'s `session` block alongside `SESSION_COMPACT_THRESHOLD_PERCENT`: `SESSION_COMPACT_THRESHOLD_MIN_PERCENT` and `SESSION_COMPACT_THRESHOLD_MAX_PERCENT` (each an integer 1-100, clamping the tuned value; a missing bound defaults to `compactThresholdPercent` itself) and `SESSION_COMPACT_TARGET_INTERVAL_MS` (a positive integer; missing means `Infinity`, which `computeTunedThreshold` treats as an explicit no-op step — never a step in either direction, regardless of how wide the min/max band is — rather than letting every observed interval vacuously count as "shorter than target"). With none of the three set, `min === max === compactThresholdPercent`, so the tuner's clamp always returns that single value regardless of observed intervals — deployed behaviour is unchanged with no new env vars, and rollback is unsetting them.

**Memory-tuned envelope sections vs. the perch full block** (Q9, Q12, R1): every Discord conductor turn runs through `ContextPolicy` (`src/agent/session/context-policy.ts`), which gates five envelope sections so each carries only what changed since it was last shown, not the whole thing every turn — the per-user `[About this user]` memory block (`shouldInjectUserMemory`/`markInjected`, R1), new memory events (`eventsDelta`/`markEventsSeen`), the state top-set (`stateTopSetDelta`/`markStateTopSetSeen`, Q9), the day's calendar agenda (`calendarDelta`/`markCalendarSeen`, Q12 — polled at most once an hour or on a local-day rollover, per-user, via `loadCalendarAgenda`), and service health (`healthNote`/`markHealthSeen`, Q12 — fed by an optional `healthRegistry`, rendered only on a state transition, including the return to all-online). The per-user memory gate is fingerprint-based rather than time-windowed (R1, replacing the old fixed-hours re-injection clock and its config field): `conductor-processor.ts` loads the block fresh on every message (one query, same as the one-shot path always did) and injects it only when its content hash differs from the fingerprint recorded at that user's last `markInjected` call — an unchanged block is never re-injected no matter how long it has been, and a changed block re-injects immediately with no elapsed time required. `src/integrations/discord/setup/conductor-processor.ts` wires all five into `buildDiscordEnvelope`'s `userMemoryBlock`/`newEvents`/`stateChanged`/`calendarChanged`/`healthNote` params and marks each seen only after a non-withdrawn `submit()` — a withdrawn (debounce-interrupted) turn never showed its envelope to Claude, so marking it would wrongly skip the real injection next time; the one exception is the memory fingerprint mark itself, which is written unconditionally on every non-withdrawn turn (not gated on whether the block was actually injected that turn), since the mark always reflects the block just loaded and re-recording an unchanged fingerprint is a no-op. `ContextPolicy.resetAll()` (called by the compaction sink once a `/compact` completes) clears every user's memory fingerprint, the state top-set baseline, the calendar poll cache, and the health mark — re-arming all four as if this were a cold start — but deliberately NOT the events mark: a compaction can run for minutes with perch active in parallel, and events written during that window must still reach the next `eventsDelta`/`eventsSinceMs` read rather than falling through a reset boundary. A `calendarDelta()` rejection (a transient CalDAV failure) is logged and swallowed rather than failing the turn: the envelope still goes out, just without a `[Calendar]` section that turn. Perch is deliberately exempt from all of this: `createPerchConductor` (`src/app/sessions.ts`) builds no `ContextPolicy` at all, and perch turns instead carry the FULL context every time via `buildPerchContext` (full agenda, full service health, top-3 state — `agent/perch/envelope.ts`'s `buildPerchSlotEnvelope` renders it verbatim, with no `calendarChanged`/`stateChanged`/`healthNote` parameters to plumb a delta through even if one existed). This is the right tradeoff for a session that runs only a handful of turns per day — each one needs to be self-contained — rather than a gap to close later.

**Background-work wake turns** (R2): launching a sub-agent, workflow, or backgrounded `Bash` fires PostToolUse inside the launching turn, and `createTaskLaunchHooks` (`src/agent/hooks/task-launch.ts`) records the launch — `taskId`/`toolUseId`, plus the launching turn's `kind`/`channelId`/`authorId` from `Conductor.status().turn` — into `TaskLaunchRegistry` (`src/agent/session/task-launch-registry.ts`, journaled as `task_launched` and seeded from that journal at boot). When the work finishes, the SDK does not resume the launching turn; instead it delivers a `<task-notification>` UserPromptSubmit wake and starts a fresh spontaneous assistant turn. That hook calls `Conductor.adoptWakeTurn`, which looks the launch up in the registry, synthesizes a `task`-kind `Envelope` carrying the launching turn's channel/author, and opens a real turn around it (journaling `turn_submitted`/`envelope_submitted` like `beginTurn`, but without re-pushing to the SDK queue, since the SDK already started this turn) — so whatever Izzy writes is journaled and delivered exactly like an ordinary reply, not dropped as a bare `notification` turn with no envelope. Delivery is `createWakeTurnDelivery` (`src/integrations/discord/setup/wake-delivery.ts`, wired via each role's `setWakeTurnDelivery` in `src/app/sessions.ts` and called from `bot.ts`'s `clientReady`): a `task` envelope with a known channel (its own `channelId`, or a well-known kind such as `perch`) delivers there via `Conductor.deliver`; one whose launch record was evicted or never found — and every `notification`-kind reply from `NotificationBridge.attachReplyDelivery` (host-submitted email/outage notifications, which never carry a channel) — routes to the `fallback` well-known channel instead of being silently discarded, prefixed to say so. Real-SDK facts (probe `probe-task-wake.ts`, SDK 0.3.258): the wake's `<task-notification>` prompt carries `<task-id>`/`<tool-use-id>` matching the launching PostToolUse's ids, and fires as a UserPromptSubmit hook *before* the woken turn's first frame — a subagent-internal task notification (`output_file: ''`, no `tool_use_id` correlation) never fires one and is ignored.

**Session peers** (`docs/plans/session-peers-and-quota.md`): the conversation and perch sessions are two independent Claude Code processes, and each registers in the machine-wide peer registry that `ListAgents`/`SendMessage` read and address, under the titles `Izzy-main` and `Izzy-perch` (`SESSION_PEER_NAMES` in `src/agent/session/query-options.ts`, set via the `CLAUDE_CODE_SESSION_NAME` env var — `Options.title` alone does not reach the registry). A `SendMessage` from one to the other arrives as the SDK's raw `<cross-session-message>`-wrapped `UserPromptSubmit` prompt; `src/agent/hooks/peer-message.ts`'s hook parses it and calls `Conductor.adoptPeerTurn` (`src/agent/session/conductor.ts`), which adopts the turn the SDK already started — rendered by `buildPeerEnvelope` (`src/agent/session/envelope.ts`) as a `[PEER · <fromName> · stamp]` envelope, journaled and ledgered as `turn.kind === 'peer'` like any other turn kind. `src/agent/prompts/system-prompt.ts`'s `buildPeerPrompt` teaches each role its own name, its other half's name, and the rule that any registry entry without the `Izzy-` prefix is most likely one of Craig's own Claude Code sessions rather than a peer. That prefix is enforced, not just documented: `src/agent/hooks/agent-naming.ts`'s `PreToolUse` hook stamps `Izzy-` onto every `Agent` launch's `name` and rewrites a `Workflow` script's `meta.name` literal the same way, so a sub-agent or workflow either session launches also reads as Izzy's in the registry. A known gap: a peer message that arrives while the receiver is already mid-turn is folded into that turn by the SDK with no `UserPromptSubmit` hook firing at all, so it never reaches the ledger or journal as its own `peer` turn (see the probe's P3 in the plan doc).

**Quota awareness**: both sessions see the shared Claude Max subscription's utilization on every turn. The SDK emits a `rate_limit_event` frame whenever the API's rate-limit headers change, carrying both the five-hour and weekly windows; `src/agent/session/ledger.ts`'s `reduceSdkFrame` normalises and folds it into `Ledger.quota` (`source: 'headers'`). Because that emission is change-driven rather than per-turn, `src/agent/session/quota-poller.ts`'s `createQuotaPoller` is a secondary refresh — polled every `config.agent.quota.pollIntervalMs` and, debounced, after every `result` frame — dispatching a `quota_polled` ledger event to both roles' stores at once; `src/index.ts` arms it with `ambience.quotaPoller.start()` in `app.start()` (next to `sagaExecutor.start()`) and `ambience.quotaPoller.stop()` in `app.stop()` (next to `outboxDrainer.stop()`) — the recurring poll is the only refresh an idle process gets, since `rate_limit_event` frames and the per-`result` debounce both require Izzy to be taking turns. `src/agent/session/ambient-lines.ts`'s `composeAmbientLines` renders a `Quota: 5-hour 42% (resets 14:00) · week 61% (resets Thu 09:00)` line — taking each window from whichever ledger holds the fresher reading — appended to the time header via `withAmbientLines`, wired at the composition root (`createSessionAmbience` in `src/app/sessions.ts`) so every producer of a time header (the boot bundle, `perch-driver.ts`, `discord/handlers.ts`, `conductor-processor.ts`, `catchup-setup.ts`, `notification-bridge.ts`) carries it without change to its own logic. `src/agent/session/quota-notes.ts`'s `createQuotaNotes` is the active side: it watches both ledgers and calls the notification bridge, always `wake: false`, when a window's peak crosses a `config.agent.quota.notifyAtPercents` threshold (default 75/90) or resets after having been at or above the lowest one — and its `isPaused()` is the perch quota ceiling, OR-ed into the `isCostPaused` predicate `src/index.ts` passes down to `src/agent/perch/scheduler.ts` (pausing scheduled perch turns once the five-hour window's peak reaches `config.agent.quota.perchPauseAtPercent`, default 90) and to presence's existing `⏸ perch` marker (`src/integrations/discord/setup/presence-setup.ts`), so no new plumbing was needed to surface the pause.
