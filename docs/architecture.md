# Isambard Architecture

Isambard is a self-improving agentic thought partner built on the Claude Agent SDK, TypeScript, and Bun. It follows a layered architecture with a single composition root (`src/app/`) that wires subsystems together; all external I/O goes through platform integrations that map at the boundary into platform-agnostic agent types. The runtime working directory is `scratch/`, which is a separate live git repo — production code lives only in `src/`.

## Module Map

## Layering

Import direction is enforced by an explicit allow-list (`eslint-boundaries.config.mjs`'s `boundaries/dependencies` rule, `default: 'disallow'` — every permitted edge is a listed policy, everything else is a lint error), not a single one-way ladder: `agent` and `email` import from each other, and so do `agent` and `bsky`. From most independent to most dependent:

```
utils     →  errors
errors    →  utils
config    →  utils, errors
storage   →  utils, errors, config
services  →  utils, errors, config, storage
agent     →  utils, errors, config, storage, services, bsky, caldav   (runtime/value imports)
agent    ⇄  email                                                     (type-only imports, both directions)
agent    ⇄  bsky                                                      (runtime/value imports, both directions)
caldav    →  utils, errors, config, storage, services                 (never imports agent)
email     →  utils, errors, config, storage, services
utraque   →  utils, errors, config, agent                             (agent import is type-only; never anthropic)
anthropic →  utils, errors, config, agent                             (runtime/value imports; never utraque)
discord   →  utils, errors, config, storage, services, agent, email, bsky, caldav
app (src/index.ts + src/app/**)  →  everything above it
```

Three named-file exceptions let a leaf module reach one layer up to throw a typed error, scoped by `fileInternalPath` rather than granted to their whole module: `utils/path-validator.ts`, `utils/media/**`, and `utils/assert-never.ts` may import `errors`.

`agent` and `email` are mutually dependent but only at the type level: neither may import a runtime value from the other, so `PlatformHistoryProvider`/`HistoryFetchParams`/`HistoryFetchResult`/`HistoryEntry` and `NotifyFn`/`ActivityLogger` flow from agent into email (`email/history-provider.ts`, `email/outbound-approvals.ts`) as `import type`, and email's client/draft types flow into `agent/email-mcp-server.ts` and `agent/context-builder.ts` the same way. Two calls are the deliberate exception: those same two agent files call `formatAddressForDisplay`/`searchDraftsByReviewState` directly and carry a scoped `eslint-disable-next-line boundaries/dependencies` naming why. `agent` and `bsky` are mutually dependent at the value level — `agent/bsky-mcp-server.ts`, `agent/context-builder.ts` and `agent/live-signals.ts` import Bluesky's client and domain types directly, and the policy lets `bsky` import agent values back, though today `bsky/history-provider.ts`, `bsky/outbound-approvals.ts` and `bsky/dm-poller.ts` only use it for the same `PlatformHistoryProvider`/`NotifyFn`/`ActivityLogger` ports, as types. `caldav` is one-way: `agent` imports it (`caldav-mcp-server.ts`, `context-builder.ts`, `session/calendar-delta.ts`, `session/context-policy.ts`) but `caldav` never imports `agent` — it provides data and does not call agent APIs, and its `/calendar` Discord slash command lives in `src/integrations/discord/calendar-commands.ts`, not in the caldav module itself.

`discord.js` and `@discordjs/*` are fenced by a second, separate mechanism (`eslint.config.mjs`'s `no-restricted-imports`, not the boundaries rule above): only `src/integrations/discord/**` and `src/app/**` may import them; everywhere else takes Discord wire types from `discord-api-types/v10`, which is deliberately not fenced. The one exemption is `src/agent/discord-mcp-server.ts`, the honestly named Discord MCP adapter the agent module hosts by convention — it carries its own inline exemption comment rather than an `ignores` entry, so the exception is visible at the import.

`src/integrations/utraque/` and `src/integrations/anthropic/` are declared `boundaryElements` in `eslint-boundaries.config.mjs`, sitting beside `email`/`bsky`/`caldav`, but the two integrations don't share one shape: `utraque/provider-capacity.ts` takes agent-owned quota types (`VendorSnapshot` and related vendor/quota types) as `import type` from `@/agent` — the type-only shape of the `agent ⇄ email` pair, though here it's one-way (`utraque` imports agent's types; `agent` does not import `utraque`) — while `anthropic/usage-fallback.ts` value-imports `fileQuotaWindow`, `hasQuotaWindow` and `unifiedAnthropicQuotaId` from `@/agent` alongside its `QuotaWindows` type import, a runtime dependency closer to the `agent ⇄ bsky` shape, again one-way (`agent` does not import `anthropic`). Both integrations may otherwise only reach `utils`/`errors`/`config`; neither may import `storage`, `services`, `discord`, `app`, or each other. `src/app/quota-poller.ts` is the sole caller of `fetchVendorSnapshot` and `fetchUsageFallback`, and no other integration imports either folder — both are also in `APP_MAY_IMPORT` and the entry-point `!index.ts` disallow list alongside the other integrations.

The composition root (`src/app/`) is the only module allowed to import from all layers simultaneously. `src/app/index.ts` re-exports its factory groups: storage (`createStorageLayer`), Discord infrastructure (`createDiscordInfrastructure`), context (`createContextLayer`), MCP servers (`createMcpSharedDeps` + `createMcpServerInstances`), identity (`loadIdentityContext`), sessions (`createConversationConductor`, `createPerchConductor`, `createSessionAmbience`), the session supervisor (`createSessionSupervisor`, `startSessions` in `runtime.ts`), lifecycle (`registerSignalHandlers`, `createDiscordRecoveryHandler`), the hot-reload guard (`registerHotReloadInstance`, `stopPreviousHotReloadInstance`), and the startup-chain single-flight guard (`createStartupChain` in `startup-chain.ts`, wrapping `startSessions` so a repeated `app.start()` within one lifecycle never reruns it). `createStorageLayer` binds a `MemoryToolBackend` to tag-index reconciliation through `createMemoryTagIndexReconciliationScheduler`, so reconciliation-specific operations do not become app-visible backend methods. These construct subsystems and inject their dependencies rather than letting subsystems find each other. `src/index.ts`, the composition root's other half, is classified separately (a `boundaries/files` entry, not a folder element) but carries the same `APP_MAY_IMPORT` allow-list plus `app` itself, so it can reach `src/app/`'s own barrel.

Platform integrations (Discord, Email, Bluesky) each own their own setup concerns. Discord is the hub for approval UI: the adapters in `src/integrations/discord/approvals/` own the cards, buttons, modals and embed parsing, and call plain email and Bluesky approval operations (`EmailOutboundApprovals`, `BskyOutboundApprovals`) whose inputs are identifiers and decisions, never interactions. The CalDAV `/calendar` slash command lives in `src/integrations/discord/calendar-commands.ts`. Outside `src/integrations/discord/` and `src/app/`, no code imports `discord.js` or `@discordjs/*`. CalDAV is independent of the agent module — it provides data but does not call agent APIs.

`src/agent/` never imports `src/integrations/discord/`, and the reverse — Discord calling into the agent — is the only edge the boundaries config allows between the two. Two conceptually distinct areas share the `src/agent/` folder: the **agent session core** (`src/agent/session/`) takes only callbacks and platform-neutral types as input and, with one exception, imports no platform integration — `session/calendar-delta.ts` value-imports CalDAV's pure time-range helpers (`resolveToInstant`, `displayDay`, `dayOrderMs`) and `session/context-policy.ts` type-imports `CalendarEvent`, both from `@/integrations/caldav`, so the session core is not the platform-neutral seam this doc otherwise describes — while the **platform MCP adapters** (`src/agent/*-mcp-server.ts`, e.g. `discord-mcp-server.ts`, `bsky-mcp-server.ts`, `email-mcp-server.ts`, `caldav-mcp-server.ts`) are where the agent module's permitted edges into email/bsky/caldav — and the one exempted `discord.js` type import — actually live. The canonical `ChannelId`/`UserId` Zod brands live in `src/config/discord-ids.ts` so config, services, the agent and Discord share one identity; `src/agent/types.ts` re-exports them for existing consumers. Discord validates live channel and user IDs before building a session envelope; message IDs remain plain strings. At the boundary, `src/integrations/discord/setup/coordinator-setup.ts` (`processAttachments`/`toPlatformImages`) and `src/integrations/discord/setup/discord-envelope-provider.ts` (`toEnvelopeInput`/`resolveNames`) together project Discord message inputs into the two-field agent envelope contract that `conductor-processor.ts` consumes; `catchup-setup.ts`/`handlers.ts` are the other envelope producers. Discord producers project source messages to `EnvelopeSourceMessage` (`messageId` and `content` only); `PlatformImage` remains agent-owned. Historical inbox rows may lack an author ID: replay keeps the display name in the rendered text but leaves author attribution absent rather than treating the name as an ID. Journal reads remain tolerant of historical plain/empty IDs; the task-launch registry validates persisted source IDs on seeding, and nonempty legacy display names in author slots age out with the 24-hour recovery read window. User-name resolution shares the agent-owned `UserResolveResult` with a branded `UserId`, and the CalDAV MCP server requires a resolver rather than treating a name as an ID. Discord's validated attachment schema is constrained to the canonical `MediaFetchMetadata` shape in `src/utils/media/`.

## Module Boundaries

Boundaries are enforced by two complementary mechanisms.

**`eslint-plugin-boundaries`** (`eslint-boundaries.config.mjs`) implements the layering allow-list above as a lint rule with `default: 'disallow'`. Every allowed import direction is an explicit policy; anything not listed is an error. The same config also enforces entry-point discipline: production code crossing a module boundary must import from the barrel (`index.ts`), not from internal files. This is the `!index.ts` catch-all disallow rule.

**`@hughescr/eslint-plugin-module-boundaries`** adds three finer-grained rules:
- `no-internal-in-barrel` — barrel `index.ts` files must not re-export symbols tagged `@internal`.
- `no-cross-module-internal` — production code must not import an `@internal`-tagged symbol from a different architectural module.
- `no-star-export-from-non-barrel` — barrel files must not `export *` from a non-barrel source file (star-exports from another `index.ts` are allowed).

**`@internal` JSDoc tags** mark symbols that are implementation details — exported for intra-module use (e.g., sub-directory to parent directory), but not part of the public cross-module API.

**Barrel export policy**: each `index.ts` conservatively exports only what other modules actually need. Over-exporting is caught by `bun dead-code` (knip). Tests may bypass the barrel and import directly from source files to access internals without inflating the public API surface.

## Data Layer

DynamoDB is the **authoritative record store**: every durable business record (memory items, contacts, channel registry, session journal, operational state, sagas, outbox, allowlist) lives in one table with PK/SK primary key and two GSIs. Semantic memory search is served separately — see "Memory vector index" below.

- **GSI1** (`GSI1PK` / `GSI1SK`): memory path-namespace-and-time index (`LAYER#<namespace>`, where the namespace is a memory path's first segment, so `/users/{id}/...` is `LAYER#users`; used for memory layer listings and time-range scans, which stay restricted to the three cognitive layers) plus the Discord channel registry's `GUILD#<guildId>` partition. Provisioned at 2 RCU.
- **GSI2** (shared partition space): multiple unrelated subsystems share this GSI using non-overlapping partition key values, not prefixes — each is one fixed literal partition key with items distinguished by `GSI2SK`:
  - `WELLKNOWN#<type>` — channel registry well-known-channel lookup.
  - `TAG_COUNTS` — the memory tool's tag index (`GSI2SK` is `TAG#<tagname>`).
  - `CONTACTS` — every contact profile item, for full-list queries without a scan.
  - `CONTACT_LOOKUPS` — every `CONTACT_LOOKUP` row, queried only by the contacts reconciler's Phase A (`src/storage/contacts/reconciliation/reconciler.ts`); everyday identifier resolution (`ContactBackend.resolveIdentifier`, `src/storage/contacts/backend.ts`) is a primary-table `Query` on the `CONTACT_LOOKUP#<platform>#<value>` partition key (`ContactKeyGenerator.createLookupPK`, `src/storage/contacts/key-generator.ts`), not a GSI read.

**Memory vector index** (`src/storage/memory-vec/`, `src/storage/memory-vec-store/`): semantic search over memory content runs outside DynamoDB. `Embedder` (memory-vec, wrapping node-llama-cpp) produces packed binary embeddings; `AsyncIndexer` (memory-vec-store) is a non-blocking worker that upserts them into a SQLite-backed `VectorIndex` at the configured `dbPath` (default `memory-vec.sqlite`). DynamoDB remains the record of truth for the memory item itself; the vector index is a derived, rebuildable search structure alongside it.

*Expiry and concurrency (#129).* Each `memory_vectors` row carries the memory's DynamoDB `TTL` (epoch seconds, NULL = never) in a nullable `ttl` column, added to older files by an idempotent `ALTER TABLE` inside an IMMEDIATE transaction. The TTL travels from the write path: `MemoryToolBackend.create` enqueues `input.ttl`, and `update` enqueues the TTL returned by `MemoryToolBackendCore.updateWithTtl` (exactly what the PutItem persisted), including for a TTL-only refresh; on a content-hash match the indexer skips the embed and only calls `setTtls`. Each row also carries a source version, `source_updated_at` (epoch ms of the DynamoDB item's `updatedAt` it reflects; NULL for rows written before it existed): every job enqueues the `updatedAt` its write persisted, the backfill sends each item's, and `upsert`/`setTtls` never replace a row holding a newer version, so a backfill page read before a live refresh or rewrite cannot roll the vector or its TTL back. `setTtls` counts only TTL changes but also advances the version when the TTL already matches (for example after `recordMemoryAccess` bumped `updatedAt`). `VectorIndex.query` hides rows with `ttl <= now`, and `createVectorPruneScheduler` (started with the app, stopped before the indexer drains) deletes them from both tables at startup and hourly (`pruneExpired`, bounded batches), with zero DynamoDB reads, because DynamoDB expires the memory itself by the same TTL. Every connection sets `busy_timeout = 5000` then `journal_mode = WAL` (`connection.ts`; a failed WAL switch is logged and the open continues), and every write transaction is IMMEDIATE, so operator tools can write while Izzy runs: a competing writer waits (synchronously, up to 5 s) rather than failing at once, and a read-then-write can neither act on a stale read nor hit `SQLITE_BUSY_SNAPSHOT`. A wait longer than 5 s still fails; the indexer retries SQLite busy/locked and embedding failures in memory for three total attempts with 250 ms then 500 ms backoff, while newer same-path work supersedes a pending retry. It logs and drops exhausted or non-transient failures, and a later backfill repairs derived data after either that drop or a restart (retry state is not persisted). `tools/prune-vector-orphans.ts` is the one-off cleanup for rows orphaned before #129; the runbook, backups and rollback are in [vector-index-operations.md](vector-index-operations.md).

*Delete tombstones close a backfill/live-delete race (#134).* A backfill page read is not atomic with the write it produces: if Izzy deletes a memory between `tools/backfill-vectors.ts` reading its GSI1 page and the matching `upsert` reaching the index, the plain `INSERT ... ON CONFLICT` in `upsert()` takes its no-conflict INSERT branch (no existing row means no `source_updated_at` guard applies) and creates an orphan row for a memory that no longer exists in DynamoDB. `VectorIndex.deleteAndTombstone(pk, sk, sourceUpdatedAt)` is the live delete path now used by `AsyncIndexer` in place of the plain `delete()`: in one IMMEDIATE transaction it deletes the row from both tables — unless a stored row's own `source_updated_at` is strictly newer than `sourceUpdatedAt` (a concurrent recreate raced ahead of a delayed delete job; the row is left alone) — and always records or advances a row in the new `vector_delete_tombstones` table (`UNIQUE(pk, sk)`, `source_updated_at`, `created_at`) to at least `sourceUpdatedAt`, even when there was no row to delete. `MemoryToolBackend.delete` stamps that version as `Date.now()` immediately after its DynamoDB delete completes (before the best-effort tag-index cleanup that follows it), since a delete carries no persisted `updatedAt` to reuse. `upsert()` now checks this table before its INSERT: an entry with no source version, or one older than the tombstone's, is refused (a tie is let through, matching the row-vs-row `>=` convention) — so backfill's `stats.superseded` count, not a new orphan row, is what a resurrection attempt produces. `pruneExpiredTombstones()`, batched like `pruneExpired()`, deletes tombstones older than `DELETE_TOMBSTONE_TTL_MS` (15 minutes — a large margin over the actual race window) and runs alongside `pruneExpired()` in `createVectorPruneScheduler`'s hourly pass, in its own try/catch so one kind's failure never blocks the other. The whole mechanism is local SQLite: zero extra DynamoDB reads, no RCU-budget impact.

*Search overfetch (#135).* vec0 KNN selects candidates before the joined TTL and stored-layer predicates (and before legacy path validation). `VectorIndex.query` therefore doubles candidate k when a pass yields fewer than the requested eligible results, stopping when full or when the whole vec0 table is exhausted. sqlite-vec 0.1.x caps k at 4096; if more vectors exist and the cap is underfilled, one exact local SQLite Hamming-distance scan covers the remaining rows. TTL and layer predicates are unchanged, and no index rebuild, DynamoDB read, or extra write is required. Selective filters cost bounded additional synchronous local SQLite work.

**Memory tool** (`src/storage/memory-tool/`) has three cognitive layers plus the `/users/` namespace, exposed to the agent via MCP. `classifyMemoryPath` (`types.ts`) is the one classifier: a path's first segment is its `PathNamespace` (what GSI1, the tag index and the vector index store as `layer`), its `cognitiveLayer` is set only for the layers in `LAYER_NAME_VALUES`, and `/users/<userId>/…` also yields the `userId`. The root `/` is a directory, never a memory item (`memoryPathSchema` rejects it). The `semantic_search` and `search` layer filters accept the three layers or `users`; `storeSelf` stays limited to identity/state, and layer listings and time scans to the three layers:
- `/identity/` — Long-lived self-knowledge, no TTL, auto-loaded every session.
- `/state/` — Working state, no TTL, selectively auto-loaded via sigmoid scoring.
- `/events/` — Time-stamped event log, TTL-based expiry, not auto-loaded.
- `/users/{userId}/` — Per-user memory, keyed by the platform user id (today the Discord author id), not by the address-book personId.

Auto-loading of `/state/` items uses `sigmoidScore()`, which combines access frequency (sigmoid activation) and recency (exponential decay) to prioritize what gets injected into context. The two host-owned metadata concepts are `MemoryAccessStats` (decoded from persisted `accessCount`/`lastAccessed`, treating malformed legacy values as zero/`updatedAt`) and decode-only `PendingRenameIndexCleanup` (the legacy rename tombstone; its writer has been removed). `MemoryToolBackend.recordMemoryAccess` atomically increments the nested count and refreshes `lastAccessed`, `updatedAt` and `GSI1SK` without replacing unrelated metadata or TTL, updating tag indices, or enqueueing vector work; legacy absent/non-map metadata and wrong-type counts are repaired conditionally (numeric negative/fractional legacy counts decode as zero, but no production writer emits them). The tag index uses per-tag atomic counters (`META_COUNT`) and fat-pointer items that carry content preview data, avoiding a centralized registry and the race conditions that come with it. A three-phase background reconciler keeps the tag index consistent and removes existing rename tombstones. Its Phase A walks `LAYER#identity`, `LAYER#state`, `LAYER#events` and `LAYER#users` (`SEARCHABLE_NAMESPACES`) and treats a tag row whose persisted `layer` differs from the path's classified namespace as stale, so `/users/` tag rows written before #58 with `layer: 'unknown'` are rewritten to `users` on the next nightly pass without touching tag counts. Every tag row it creates or refreshes (like every row `updateTagIndexItems` writes) carries the memory's full normalized tag set as `tags`, even when only one row is rewritten, because multi-tag AND search re-checks every requested tag on that attribute and the staleness check compares it to the memory's tags. Since #132 the reconciler paces every DynamoDB pagination loop across all three phases (Phase A's `LAYER#*` GSI1 scan, the GSI2 `TAG_COUNTS` tag-name/tag-count enumeration shared by Phase A's legacy rename-cleanup fallback, Phase B and Phase C, Phase B's per-tag base-table scan, and Phase C's per-tag `COUNT` scan) by each page's reported `ConsumedCapacity`, defaulting to each resource's own provisioned RCU/s (GSI1 2, GSI2 1, base table 5; `reconciliation.rateLimitRcuPerSec` overrides all three uniformly) rather than per-item work, so a run of tagless, non-renamed items no longer bursts unpaced against a 2 RCU index.

*Vector-index labels and the one-time rebuild (#58).* Live indexing and `tools/backfill-vectors.ts` both label a row with `classifyMemoryPath(path).namespace`, so `/users/` rows are `users` either way. SQLite rows written before #58 still say `unknown` for `/users/` paths, and the indexer's content-hash check will not rewrite unchanged memories, so `semantic_search` with `layer: users` misses them until they are re-embedded. After deploying #58, run the forced backfill once, under SST shell: `sst shell -- bun tools/backfill-vectors.ts --force` (back up the SQLite file first; `--dry-run` previews; `--layer users --force` is the minimal variant). A bare run walks all four namespaces through GSI1, nested paths included; `--layer` accepts only those four names and rejects typos. Each GSI1 query reads at most four items (`Limit`) and requests `ReturnConsumedCapacity: TOTAL`; before the next query the tool pauses for that page's reported read units divided by `--rate-limit-rcu-per-sec` (default 2, GSI1's provisioned capacity), less the time already spent embedding. Large items (a ~300 KB memory costs ~37 RCU) and rows `listByIndexNamespace` drops as malformed are therefore paid for in full, so the average read rate stays at or below the budget; a single page may briefly exceed it (bounded by four items, absorbed by DynamoDB burst capacity) and is paid back before the next read. If DynamoDB omits `ConsumedCapacity` the run stops rather than read unpaced (the pacing primitives live in `src/storage/utils/rcu-pacing.ts` (importable from `src`, unlike `tools/`) and `tools/rcu-pacing.ts` re-exports them for the orphan prune). Rebuild time therefore scales with total bytes read, not item count. Since #129 the backfill also carries TTL: every row it writes gets the item's `TTL` (GSI1 projects ALL attributes, so this costs no extra reads), unchanged rows get their TTL stamped in one batched `setTtls` per page ("TTL updated"), items already past their TTL are not hashed or embedded ("Skipped (expired)") but have their TTL stamped onto any existing row so the local prune removes it, and an embedded item whose row a newer live write already produced is left alone ("Skipped (index already newer)"); `--dry-run` writes no TTLs. `VectorIndex.query` derives each result's `layer` from its validated path and logs and skips legacy rows whose keys do not decode to a memory path (including root `/`); the backfill likewise logs and skips malformed paths rather than inventing a sentinel.

**Contacts** (`src/storage/contacts/`) provide a cross-platform address book. Each contact record holds a set of platform identifiers (Discord user ID, email address, Bluesky handle, etc.). Everyday identifier-to-contact resolution is a primary-table `Query` on the `CONTACT_LOOKUP#<platform>#<value>` partition key (see "Global secondary indexes" above); the `CONTACT_LOOKUPS` GSI2 exists only for the reconciler's Phase A. A two-phase reconciler handles orphan cleanup and missing-lookup repair. A contact's key is its `PersonId` (branded kebab-case); identifier equivalence (`normalizeIdentifierValue` / `contactIdentifierKey` in `src/storage/contacts/types.ts`) is shared by the lookup keys, the backend and the person allowlist.

**Person allowlist** (`src/storage/person-allowlist.ts`) gates outbound writes (email sends, Bluesky posts/DMs) by person ID rather than per-platform raw addresses. A reverse-map resolves any known identifier to its person ID for allowlist checks.

**Session journal** (`src/storage/session-journal/`, long-lived conductor sessions only): every observable session-lifecycle fact — envelope submission, turn completion, delivery, background-task start/completion/loss, compaction, session open/close — is written through to its own `SESSION_JOURNAL#<role>` partition, one role (`conversation` or `perch`) per partition, deliberately outside `/events` and carrying no GSI1 keys so these rows never enter the memory tool's tag index, embedder queue, or `LAYER#events` time-range scans. Crash recovery (`src/agent/session/recovery.ts`) reads a role's journal window at boot and derives which background tasks never reached a terminal state and which turns finished without a confirmed delivery, so the conductor can report the former as lost and redeliver the latter, deduplicated by an in-memory delivery guard (`src/agent/session/delivery-guard.ts`) seeded from the journal's own `response_delivered` rows — a crash in the narrow window between sending a reply and the journal flush that marks it delivered can still cause a redelivery on the next restart, since recovery only knows what the journal recorded. The compaction summary is not written to this journal or the memory tool's `/events/` layer at all; it stays only in the SDK's own transcript for that session. The SDK's per-session transcript files (`~/.claude/projects/<project>/`) are retained indefinitely now that both conductor sessions are long-lived — there is no startup sweep to prune or wipe them.

**Operational state** (`src/storage/operational-state/`): integration replay cursors — Discord per-channel inbox checkpoints and Bluesky feed, notification and DM checkpoints — are operational state, not memories. Each lives in an `OPERATIONAL_STATE#<owner>` partition (`discord` or `bsky`) with the key name as the sort key (e.g. `channels/<channelId>/checkpoint`, `dm/checkpoint`) and the JSON value in `content`. Rows carry no GSI1 keys, no tag rows and no embedder job, so a cursor that is rewritten on every message never reaches state scoring, hot state or semantic search; a dedicated partition is used rather than a flag on memory rows because a flagged memory row would still sit in `LAYER#state`. Reads are strongly consistent (`ConsistentRead`), because the Discord checkpoint manager's per-channel read-modify-write treats a miss as "no newer row exists". During the transition, a miss reads the legacy `/state/services/<owner>/<name>` memory row read-only (info-logged once per key per process); legacy rows are never written or deleted here, and prefix listing (boot replay's `CheckpointManager.listAll`) sees only the new partition. Copying the legacy rows across, removing that fallback and deleting the legacy rows is the separate checkpoint-migration step (#57).

## Agent Subsystem

The agent module contains the core plus per-platform MCP adapters. Its enforced dependency invariant is that `src/agent/` never imports `src/integrations/discord/`; Discord integration code calls into the agent, never the reverse. Discord-specific MCP ports are declared in `src/agent/discord-ports.ts`, and `src/agent/discord-mcp-server.ts` owns the agent module's single `discord.js` type import.

The agent exposes its capabilities to Claude through a suite of **custom MCP servers**: memory (view, store, search, log), Discord message history, email (inbox, send, archive, reply, drafts), Bluesky (feeds, posts, DMs, social graph, rejection management), Discord inbox (unread overview, channel summary), CalDAV (calendar events), contacts (lookup, search, create, update, delete), media processing (video analysis, spectrograms), Wikipedia, user context, and health (read-only per-service status, deliberately reachable during an outage). Browser automation (`src/agent/browser-mcp-server.ts`) is attached only for the `conversation` role, and only when a `browserAdapter` and its byte limits are configured (`src/app/mcp-servers.ts`'s `createMcpServerInstances`); the perch role never gets a browser MCP server, and an unconfigured deployment gets none at all.

Supporting machinery within the agent module:
- **Context builder**: assembles the per-turn user message prefix by loading auto-load memory items, perch context (email inbox state, Bluesky DM notifications, rejected posts), and calendar events.
- **AnswerClassifier**: LLM-based (Haiku) classifier that determines whether an incoming message is an answer to a pending question, an interruption, or an unrelated message.
- **QuestionRegistry**: tracks pending questions with timeouts; routes button-interaction answers back to the waiting handler.
- **StreamTracker**: accumulates a stream's latest thinking/text/pending-tool-use and the session id captured from `system/init`, so an interrupted turn's partial work can be captured (`conductor.ts` instantiates one per turn). It does not itself decide anything about resumption — a background task that never reaches a terminal state is detected at boot from the role's session journal (see "Session journal" above), not by StreamTracker or any per-turn auto-resume.
- **PersonHistoryCoordinator**: aggregates cross-platform message history from Discord, Email, and Bluesky providers, keyed by contact person ID. Providers return a typed `HistoryFetchResult` (entries plus complete/partial/unavailable coverage and per-source failures) and receive a typed per-platform `HistoryScope`; the coordinator's observed result carries a coverage block (queried, unavailable, partial, notConfigured, notApplicable, truncated, failures) so "no history" is distinguishable from "could not look". `getPersonContext` passes health-registry state so platforms already down are reported by category instead of searched.

**Perch system** (`src/agent/perch/`) provides time-based autonomous activity scheduling. A cron-based scheduler (`scheduler.ts`) uses jitter (cron-parser H option) to trigger perch slots at graduated suggestion levels depending on the hour; each trigger calls `createPerchDriver`'s `runSlot()`, which submits the slot as a turn on perch's own long-lived conductor session (design doc section 6/9 — there is no separate one-shot perch "session runner"). Deferral against an already-running slot is the driver's job, not a bot-wide mode machine: a trigger that fires mid-slot just sets a pending flag, resolved to whatever slot the clock says it is once the running turn settles. Near the end of a slot the driver submits a `[WRAP-UP]` envelope at the highest submit priority so it runs as the conductor's very next turn; past a grace period after that it interrupts an overrunning turn via `conductor.interruptCurrent()`. A perch-channel Discord message arriving mid-slot is not suspended/resumed against a separate session — `handlers.ts` submits it as an ordinary turn on the same perch conductor, queued behind whatever is already running (see `src/agent/perch/README.md`).

**Agent / skill / plugin definitions** live outside `src/` in `agents-skills-plugins/` (subagent `.md` files, skill directories with `SKILL.md`, and `plugins.json` for marketplace plugins). These are content artifacts, not code. At startup, `src/agent/skill-agent-loader.ts` copies them into `scratch/.claude/agents/` and `scratch/.claude/skills/` so the Claude Agent SDK's auto-discovery picks them up from the runtime working directory.

## Platform Integrations

Each integration in `src/integrations/` owns its full vertical slice: types, errors, client, history provider, and any approval or saga machinery it needs.

**Discord** is the primary operator interface. The bot (`bot.ts`) is the Discord adapter, delegating to setup modules in `src/integrations/discord/setup/`: it signals readiness (`bot.ready`) once the guild cache, the wake-turn delivery binding and the channel registry exist, attaches the post-open Discord wiring for whichever sessions opened (`bot.attachSessions`: presence, task board, perch driver, message processing), and supplies the replay/ingress-gate boot recovery adapter (`bot.recoveryAdapter`). It never opens, shuts down or recovers a session itself: the session supervisor in `src/app/runtime.ts` owns that open/exit/shutdown/recovery policy, sequenced by `startSessions` from `app.start()`. There is no bot-wide operational-mode state machine (the `state/` directory and its `BotStateManager` were retired once the conductor model landed) — instead, presence is *composed*, on every tick, from the two session ledgers themselves (`presence/presence-view.ts`'s `composePresence`): which of `conversation`/`perch` currently has an open turn, task/workflow/monitor counts from `Ledger.tasks`, and a compacting marker, rendered to a Discord custom-status string and throttled by a shared `PresenceThrottle` (design doc section 8). `presence/manager.ts` applies that composed view; there is no subscribe-to-mode-transitions step, no explicit idle bootstrap (the very first compose, before either ledger has emitted an event, already renders idle), and no separate presence path for "catching up" — a startup catch-up run is just turns on the conversation conductor.

The Haiku **turn synopsis** — a one-line description of what a turn is doing — is a session-core fact, not a Discord one: it lives on `LedgerTurn.synopsis`, is set by a `turn_synopsis { turnId, text, at }` ledger event matched on `turnId` only (a stale or repeated one is a no-op), and a phase flip or compaction never touches it. It has two readers: Discord presence renders it (`composePresence` copies the WINNING turn's synopsis and id into `PresenceView.synopsis`/`turnId`; `PresenceManager.applyView` shows it in place of the active generator's static label), and `ambient-lines.ts` puts the OTHER session's `turn.synopsis` into this session's prompt as "working on …". It is produced at exactly ONE point, the session core's `src/agent/session/turn-synopsis.ts` `attachTurnSynopsis`, wired once per session by `src/app/sessions.ts` next to the conductor and ledger it builds (before `open()`, fire-and-forget like the compaction tuner), each session with its OWN `createSynopsisGenerator` instance (`synopsis-generator.ts`; P14: a shared one let one session abort the other's call) and its OWN `SynopsisBudget` (at most one generation START per 12 s per session; it spends itself on every true answer). So the synopsis the other session reads never depends on Discord presence being configured, and Discord presence (`setupConductorPresence`, which now takes just the `ledgers`) only composes and renders under its display `PresenceThrottle`. Its synopsis-arrival throttle bypass — keyed on the winning `(role, turnId)`, so a new turn is never mistaken for a refinement — is the one documented exception to "at most one non-idle update per 12 s": its bound comes from the producer (each session's budget plus the generator's cancel-and-replace means at most two arrivals per session in any 12 s), and a synopsis from the non-winning session never reaches the view. The producer keys off the ledger's own turn — opening a `createSynopsisStreamHandler` (`synopsis-stream-handler.ts`) when `ledger.turn.id` changes and completing it when the turn closes — so EVERY turn kind gets a synopsis (bare notification, adopted task wake, peer message, catch-up, perch, wrapup, continuation, and the human Discord turn), not just a human message. `conductor-processor.ts` wires no synopsis handler; it keeps only its `StreamTracker` subscription for partial-work capture. `compact` is the one deliberate exclusion (`SYNOPSIS_EXCLUDED_KINDS`) — the ledger already renders a `compacting` marker and the envelope text is the literal `/compact`. Two invariants hold the attachment together: (1) every `turn_synopsis.turnId` comes from `ledger.turn.id`, never from `subscribeTurn`'s `turnId` argument — those two disagreeing (`'notification'` versus `notification-<ms>`) was the original dropped-synopsis bug, since `reduceTurnSynopsis` requires an exact match; (2) `conductor.ts` dispatches `spontaneous_turn_opened` BEFORE `notifyTurnSubscribers` on BOTH unbidden-turn paths — `beginSpontaneousTurn`, and `onFrame`'s `awaitingTurnEnd` branch, where the conductor deliberately declines to claim `currentTurn` (a `/compact` turn may be about to take it) but the ledger opens a turn anyway — so the handler exists for the turn's first frame. Without the second, a turn whose only assistant frame lands in that window would get its handler after that frame had already been routed, and for the common one-assistant-frame-then-result shape would stay generic for its whole life. `reduceAssistantFrame`'s own null-turn branch is kept as a defensive backstop for any driver that does not observe this protocol. `attachTurnSynopsis` also adopts a turn that is already open at attach time (`ledgerStore.get()`), because `LedgerStore.subscribe` does not replay the current value. Every seeded turn's handler — adopted or not — dispatches its seed synopsis as soon as it resolves rather than waiting for a `thinking` transition: the seed spends the session's budget, so a tool-first or text-first turn (or an adopted one whose next frame is the `result` that closes it) would otherwise have its seed generated, paid for and discarded and no synopsis for a whole window. The seed is still dropped once the turn completes or once anything fresher has been dispatched. The generator is seeded from `Envelope.synopsisSeed` (carried to `LedgerTurn.seed`) rather than `Envelope.text`, because `text` opens with a `[KIND · stamp]` header plus the time header plus the ambient quota lines and the generator only reads its first `SYNOPSIS_SEED_CAP` (200) characters — one exported constant in `agent/session/envelope.ts` that `synopsis-generator.ts` imports, rather than a second local copy that could drift into being unreachable. The idle Discord status's "last thinking" context comes from the producers' `onThinkingContentUpdate`, buffered in `src/index.ts` and read by the bot through its `getLastThinkingContent` option. (Tool and MCP server selection is not mode-driven; the inbox server is attached to every turn.) The channel registry is DynamoDB-backed with write-through cache and supports well-known channels (`general`, `catch-up`, `perch-time`, `fallback`). The inbox system tracks unread messages with per-channel checkpoints in the operational-state store; a startup catch-up turn drains the backlog through the conversation conductor rather than a separate catch-up session. Discord reply classification (`ResponseRouter.resolveDeliveryTarget`) is synchronous and origin-first: a recorded start channel wins, otherwise catchup maps to `catch-up`, perch and wrapup map to `perch-time`, and all other channel-less replies require caller-managed `fallback`. The perch task-wake delivery projection deliberately removes its launch channel (without modifying the original envelope or journal), so it still routes to `perch-time`. Missing mapped channels are skipped by the sender rather than silently sent to fallback.

The **task board** (`presence`'s sibling, `src/integrations/discord/task-board/`) is composed from the same ledgers: `LedgerTask` now tracks every non-ambient sub-agent, workflow and background shell command (foreground sub-agents included, ended by their `tool_result`), with the latest `task_progress` usage, the SDK's AI progress summary, and a workflow's parsed `workflow_progress` (phases and per-agent state), and finished tasks linger in `Ledger.finishedTasks`. `composeTaskBoards` groups tasks by launching channel and turn (a conversation task whose turn had no channel boards in the `fallback` well-known channel); `renderTaskBoardEmbed` is a pure renderer to a Discord embed (ten-cell meter, tokens, elapsed, kind emoji shared with presence); `TaskBoardManager` posts one embed per board and edits it through a trailing-edge throttle (`discord.taskBoard.editIntervalMs`), with a final edit on completion and never again. Design: `docs/plans/task-board.md`.

**Email** uses the WildDuck HTTP API for all operations (read, search, send, flag management, draft upload). SSE push with poll fallback drives real-time inbox notifications. Outbound sends require admin approval via Discord unless the recipient is on the person allowlist. A `TokenBucketRateLimiter` (`src/services/rate-limiters/token-bucket.ts`, built in `email-setup.ts` from `email.sendReservoirCapacity`/`email.sendReservoirRefillRatePerHour`, default capacity 24 / refill 1 per hour) tracks send volume; an approved send still goes through when the bucket is empty — the limiter only appends a "rate limit reached" warning to the confirmation, it never blocks the send. Custom keyword flags use no `\\` prefix — WildDuck HTTP convention, not IMAP.

**Bluesky** wraps `@atproto/api`'s `AtpAgent`. DID projection is per-tool, not uniform: `listConversations` (via `transformConversation`) and `getDirectMessages` (an inline DID→handle map built from the conversation's members) both replace `senderDid` with a resolved handle before returning; `getProfile`, `getPost`, `getAuthorFeed`, `searchPosts` and `getFeed` return the client's result as-is, DID unprojected. Outbound replies and DMs flow through an approval workflow with Discord buttons/modals. Admin rejections are persisted to a `BskyRejectionBackend` (DynamoDB, 30-day TTL) and surfaced back to the agent in perch context so it can retry or acknowledge them. Feed, notification and DM consumption is idempotent via a checkpoint manager backed by the operational-state store (see "Operational state").

**CalDAV** stores per-user credentials in DynamoDB (no global SST secrets). Discord `/calendar` slash commands manage credentials. The agent accesses calendar data through the `caldav-mcp-server` MCP tool; CalDAV itself does not import from the agent module.

`CalendarEvent.time` is a `CalendarTimeRange` with three variants, built only through the checked `createCalendarTimeRange` constructor (`caldav/types.ts`): `all_day` holds `YYYY-MM-DD` dates with an exclusive end and never shifts across zones; `floating` holds offset-free wall-clock date-times; `timed` holds validated instants plus the source timezone. The client (`buildTimeRange` in `caldav/client.ts`) classifies node-ical's output: DATE values and zone-less DATE-TIMEs are read back from host-local components (node-ical builds them that way), a `tz`-tagged Date is timed, and a floating RRULE instance takes the series DTSTART's wall time on its nominal date because node-ical expands floating rules in UTC. A VEVENT whose time cannot be decoded lands in `failed[]` beside its neighbours instead of failing the server fetch. One display-zone policy (`caldav/time-range.ts`) serves the formatter, the session agenda and the Discord change list: floating times resolve in the viewer's zone (a DST-gap time shifts forward, a repeated time takes the earlier instant), and all-day ranges group under their own date and overlap a day window by date with the exclusive end. Raw merged events sort by a zone-independent date/variant/time key. The CalDAV MCP tools return the discriminated `time` object and never synthesize an instant for a date or a floating time. The day's agenda projection and fingerprint keep the variant, so a floating 09:00 and a timed 09:00Z differ; `ContextPolicy` keeps the calendar baseline in memory, aligned to the viewer's local day.

The registry's `CalendarRegistryScope` distinguishes `personal` from `shared` without a pseudo-user. `CalendarRegistryKeyGenerator` owns the persisted form: the unchanged `CALCAL#{userId}` / `CALCAL#SHARED` PKs, `parseScope` to decode them, and the single `SHARED` literal. Reads derive the scope from the authoritative PK, so pre-scope rows need no backfill and a conflicting body `userId`/`scope` is ignored. Every write keeps the legacy `userId` body attribute (`SHARED` for the shared record), so a pre-scope build can still read the row during rollout or after a rollback. That attribute can be dropped once no such build can run.

Discord's setup producers project their message inputs to the two-field agent envelope contract at each call to `buildDiscordEnvelope`; `coordinator-setup.ts` separately handles attachment processing and other coordinator wiring. The other platform setups (`email-setup.ts`, `bsky-setup.ts`, etc.) handle their own initialization and wire approval callbacks back into the Discord approval infrastructure.

## Services Layer

`src/services/` provides resilience and workflow infrastructure:

- **ServiceHealthRegistry** (`health-registry.ts`): registers named services and tracks their health status via `sendEvent(service, event)`, for observability. `HealthState` (`services/types.ts`) gates MCP tool availability (`agent/mcp-helpers.ts`) and approved-outbound-action execution (`services/approved-outbound-action/executor.ts` skips an action whose required service is unavailable).
- **ReconnectionLoop**: wraps external service connections with exponential-backoff auto-reconnect.
- **`serviceLifecycleMachine`** (`lifecycle-orchestrator.ts`): a per-service xstate state machine tracking connect/disconnect/retry transitions, epoch, failure count and last error, driven by `ServiceHealthRegistry.sendEvent`; overall process startup/shutdown sequencing lives in `src/index.ts`'s `createAppLifecycle`/`buildAppLifecycle`/`runShutdownSteps`, not here.
- **TokenBucketRateLimiter** (`rate-limiters/token-bucket.ts`): generic refill-over-time token bucket, used by both the email send limiter and the Bluesky rate limiter.
- **Error boundary** (`error-boundary.ts`): process-level `uncaughtException`/`unhandledRejection` handlers.
- **Outbox pattern** (`services/outbox/`): DynamoDB-backed Discord-post outbox drained on Discord-online transitions, after `DiscordCapability` queues a send (its `onQueued` wake, because a send queued while Discord stays online gets no transition), and via one replaceable delayed-retry timer. A drain requested while one is active (a timer firing, an enqueue wake) is remembered and runs one drain interval after the active drain settles, so it is never lost. Failed work persists capped exponential backoff and does not block later ready rows; legacy rows without delay metadata remain immediately eligible. Known Discord rejections may be classified by the optional Jev port: high-confidence permanent failures are discarded as `classified_abandon`, while unavailable or uncertain classification falls back to bounded retry. An uncertain send outcome is durable `unknown` and is never blind-replayed: every text chunk and embed/component-only payload carries one complete invisible zero-width delivery code, derived from its chunk token and appended only after splitting. The reserved UTF-16 content budget keeps the code and chunk at or below Discord's 2,000-code-unit limit; history must decode every expected code before acknowledgement, while bounded REST history that cannot determine delivery is rechecked rather than resent. Discord nonce/enforceNonce provides only short-window immediate deduplication and is not a history correlation key. DynamoDB TTL automatically expires rows, without an application-observed discard; for items without an explicit `ttl`, retry writes refresh the default 24-hour TTL, and DynamoDB expiry itself can lag. Malformed rows (including invalid branded destination IDs) are deleted on dequeue, logged with PK/SK, and paginated Queries continue past them to find valid work in priority order; deferred rows are skipped while pagination continues, and every scan reports their `nextAttemptAt` so the drainer re-arms a retry timer that a shorter full-batch continuation displaced.
  - *Izzy's Discord tool sends (#138).* A plain-text `sendDiscordMessage` goes through `DiscordCapability.sendText` as ONE outbox item per message (type `agent_response`, priority `high`), not one item per chunk: the first send and every replay split it with the same `messageChunksFor`, each part carries its own complete delivery code and nonce, and part 0 carries the reply reference (`payload.replyToMessageId`, sent with `failIfNotExists`, so a reply is never posted without it). `progress.deliveredParts` records the confirmed prefix, so neither a failed immediate send nor a partial replay resends delivered parts; after an unknown outcome the replay also advances past any part whose code is in history (parts go out in order, so a later part's code proves the earlier ones), and records that history-confirmed prefix in `deliveredParts` before sending, because a definitive rejection of the next part persists it as a retryable outcome that the following replay trusts without history. `markFailed` keeps `deliveryToken` and `deliveredParts`, because part boundaries are sized from the token. Indeterminate failures, and a Discord that is not ready, queue the whole message and the tool reports `queued` (or `partially_sent`); definitive rejections are reported as not sent and are not queued. When a replayed reply is definitively rejected, the replay re-fetches the target bypassing the cache: on Unknown Message (10008) it notifies Izzy through the notification bridge (source `discord-outbox`, key = outbox id, wakes, with the channel, target id and full undelivered text) and the drainer discards the item as `reply_target_deleted` without classifying it; while Izzy cannot be told (`notify` returns false) the item is deferred for 30 s through `OutboxBackend.defer`, which does not spend an attempt. Sends with attachments or `createThread`, and `askUserQuestion`, are deliberately direct: they keep the health check, are never queued, and report a failure as "delivery could not be confirmed" with any confirmed message ids. While Discord is unavailable `@username` cannot be resolved, and neither the channel nor a reply target is checked until replay. The `email-setup.ts`/`bsky-setup.ts` direct `channel.send` fallbacks run only for callers that omit the capability; production always passes it.
- **ApprovedOutboundAction** (`services/approved-outbound-action/`): a durable DynamoDB record of an outbound Bluesky reply/DM or email send that an admin has already approved in Discord, so it survives service outages until executed. Rows are born `approved`; rejections are not stored here (email rejections live in the draft's WildDuck metadata, Bluesky rejections in `BskyRejectionBackend`). After that approval row is durable, the email and Bluesky adapters best-effort log their respective `*-approved` activity; only after an external send and a durable `executed` settle does the executor best-effort log `*-sent`. An activity-log failure cannot change the action or outcome state. Before any external call the executor *claims* a row (`approved → sending`, storing a fresh random `claimId`), sends it, then *settles* the claim: `sending → executed`; `sending → failed` labelled `permanent` (unparseable params, Bluesky validation errors, Bluesky 4xx other than auth/rate limit) or `transient` (the request was refused or never made: Bluesky auth/rate limit, WildDuck 401 or non-404 4xx, a WildDuck error raised before any request, a missing client); or `sending → unverified` when the outcome is unknown (#108, below). When a service comes back online, `retry-on-reconnect.ts` resets that service's `failed(transient)` rows to `approved` — except a `failed(transient)` row with no `firstClaimedAt`, which an older build may have labelled transient after an ambiguous error, so it goes to `unverified` to be checked first; permanent and pre-#40 unlabelled failures stay failed. `assertTransition` rejects every other move, including sending without a claim and resending an `unverified` row without a check. Every move is a whole-row put with the 30-day TTL recomputed from `createdAt`: a claim is conditioned on the listed state and `updatedAt` revision; a settle on the row still being `sending` under the settling claim's own `claimId` (never on a wall-clock revision, which two claims could share); a reset reads the row consistently first and is conditioned on its state, revision and `failureKind = transient`; a check's resolution of an `unverified` row is conditioned on its listed state and revision.
  - *Claims, lanes and timeouts (#102).* The claim is the cross-process guard: of two processes (a deploy overlap, a stacked hot reload) that list the same `approved` row, only the one whose conditional claim lands sends it; the other logs "already claimed elsewhere" and skips. If the settle write fails after a send, the executor keeps the outcome in memory and retries only the write on later passes — never the send; a settle that finds its claim already resolved is logged and dropped. Each send is bounded to 120 s (`DEFAULT_SEND_TIMEOUT_MS`, above WildDuck's own ~90 s worst case) and aborted at its deadline; a timeout settles `unverified`. A late success conditionally resolves only that exact settled revision to `executed` (the normal sent activity and outcome-reporter wake then follow); a late failure is only logged, and a conditional loss leaves the destination check authoritative. A `sending` row whose claim is older than the 15-minute lease (`DEFAULT_CLAIM_LEASE_MS`; the process died, or restarted after its settle write failed) is swept to `unverified` too, so the card and Izzy are told instead of the row sitting stuck. The executor runs one lane per service (Bluesky, email), each its own `createSingleFlightLoop` with its own poll timer and backoff, so a hung send in one service never delays the other, including rows approved while the hang lasts; within a lane rows go strictly one at a time in listed order. What this guarantees is claim exclusion across processes and no blind resend after a recorded send, a failed settle write, a timeout, an interrupted claim or an ambiguous error. Deploy caveat: a build from before #102 does not claim, so stop the old process before starting the new one; rolling back leaves any `sending` row unparseable to the old build (warned and skipped, never resent).
  - *Outcome unknown: check the destination, then decide (#108).* `classifyFailure` (`executor.ts`) labels an error `ambiguous` unless it proves the message was not delivered: Bluesky status 1 (network failure or abort) or 2 (unreadable response to a 200), any 5xx, a status-less `BskyError`, a WildDuck 404 on submit (the draft may already be in Sent Mail) or 5xx, a fetch `TypeError`, a `TimeoutError`/`AbortError`, and anything unrecognised. An ambiguous error, the send timeout and a swept claim all settle `sending → unverified` (counting one more `ambiguousSends`), and the card turns amber ("Outcome unknown — checking … before any resend") with a note to Izzy that does not wake her. Each lane pass then checks its service's due `unverified` rows while the service is available (`delivery-verification.ts`, bounded by the send timeout): found at the destination → `executed` (green card, `*-sent` activity); definitely absent → `approved` and resent in the same pass; undecided (the check threw, timed out or could not attribute a match) → left `unverified`, never resent, and checked again later for as long as it takes — there is no automatic give-up. The first check waits 5 min after the outcome became unknown (`DEFAULT_VERIFY_DELAY_MS`), so a cut-off request the server is still processing can land first; that wait doubles with each earlier unknown send, which also paces resends to a destination that keeps answering ambiguously without delivering; undecided rechecks double from 5 min too; every wait is capped at 1 h (`MAX_VERIFY_INTERVAL_MS`). The recheck schedule is in memory, keyed by row revision, so a restart only checks sooner. The destinations (`integrations/*/delivery-check.ts`), searched from the row's first claim (`firstClaimedAt`, recorded by the first claim; the approval time for older rows): **email** — the draft's Message-ID and Date, read at approval (bounded to 10 s and cancelled; best-effort, the action is recorded without them if the read fails) and stored in the params: found in Sent Mail → delivered; otherwise the draft still in Drafts, still the same message, still a draft and with its Date unchanged → absent (WildDuck rewrites the Date before it queues a submit); a vanished draft, a changed Date or no fingerprint → undecided. **Bluesky reply** — the account's own post records read from its PDS (`listRecords`, newest record key first), matched on parent URI and exact text; the scan stops at the first record whose TID key is more than a 5-min clock margin before the window (never at a record's own `createdAt`, which a client can set), and a listing out of key order is undecided. **Bluesky DM** — the conversation's message log, matched on our DID and exact text; a deleted message of ours in the window is undecided. For both Bluesky checks a match must be inside the window by its timestamp — from the first claim to when the row's outcome became unknown (its `updatedAt`, passed as `until`), plus the 5-min clock margin past that end; an identical message stamped later is someone else's and ignored. An identical message just before the window (within the margin) or several identical ones make the check undecided. A match is also undecided while any other approved action with the same content (per its `contentKey`) was written within 15 min of either end of this one's window; the actions are listed only after the destination answered, so an identical action created during the check is seen, and a definite absence is trusted whatever identical actions exist. So neither a pre-existing or later message nor a sibling action's delivery is ever taken for this one's. Each check reads at most 5 pages of 100 (Bluesky) or 4 of 250 (WildDuck). Rollback caveat: a build from before #108 cannot parse `unverified` rows (warned and skipped, never resent), so resolve them by hand before rolling back. Before relying on it in production, confirm once against the real services that `listRecords` without `reverse` lists newest key first, and that the deployed WildDuck's submit rewrites the draft's Date and keeps its Message-ID in Sent Mail.
  - *Prompt sending.* The approval code writes rows through `createWakingActionWriter` (`waking-writer.ts`), which wakes the executor once the row is durable, so an approved send goes out within seconds instead of on the next poll (30 s backing off to 5 min). The reconnect listener also wakes the executor after its reset pass. Every lane run — poll, wake or `executeOnce()` — goes through its lane's single-flight loop (`single-flight-loop.ts`), so one lane's runs never overlap; wakes during a run coalesce into one follow-up run. The open-row listing (`approved`, `sending` and `unverified`) is a strongly consistent query, so a follow-up run never sees a row as `approved` after its claim.
  - *Approval card and outcome reporting.* Each row carries `approvalCard` (`{ channelId, messageId }` of the Discord card the admin clicked; absent on older rows). At click time the adapters first write the row and only then edit the card to a blurple "Approved ✓ — sending…/posting…" embed, so a crash between the two leaves the original card (controls and Bluesky payload intact) rather than a "sending…" card with no row behind it; a failed pending edit after the write is only logged. To stop that pending edit landing after a fast outcome edit, the click holds the card on the in-process `ApprovalCardEditGate` (`integrations/discord/approvals/card-edit-gate.ts`) for the write + edit, and the outcome delivery waits on it before editing (after a restart nothing is held, so nothing waits). Every terminal write, and the interim `unverified` one, sets `outcomeReportPending` in the same put — a durable outbox; a retry reset (and a check that resends) drops it. `createApprovedActionOutcomeReporter` (`outcome-reporter.ts`, also single-flight) lists pending rows with a strongly consistent query and delivers each through `createApprovedActionOutcomeDelivery` (`integrations/discord/approvals/outcome-delivery.ts`): a notification to Izzy via the shared notification bridge (text from `outcome.ts`; failures always wake, success wakes only for email) and an edit of the card through its channel (green sent, amber will-retry, red failed). After accepted notification handoff to Izzy, delivery conditionally persists `outcomeNotified` for that pending state/revision before attempting the card edit. A restart with an unfinished card reads that flag and retries only the card, not Izzy's notification; refused notification leaves it absent. The pending and notified markers are removed atomically, conditioned on the reported revision, only once both halves succeeded; every transition (retry reset, claim, settle) also drops the old notification flag. An unreachable Discord or a conductor that refuses the notification leaves the report for a later pass, never re-sending the action. This is best-effort deduplication: a crash or database failure precisely between the external notification acceptance and persisting its marker may still result in a duplicate after restart; writing the flag first would instead lose a notification. `notify` acceptance means conductor handoff, not completion of Izzy's turn. The executor wakes the reporter after each terminal write, and Discord coming back online wakes it too. The card's channel is looked up with the raw Discord client, which rejects on failure, so a transient lookup error (reset connection, REST timeout) is retried like a transient edit error; only a card that can never be edited (channel gone or not text-based, message deleted, missing permissions) is logged and skipped. Rows without a card are only notified.
- **AllowlistSaga** (`services/allowlist-saga/`): multi-step Discord UI flow (button → modal → confirm) for adding a contact to the person allowlist. Persisted state is a zod discriminated union (`pending_name` / `pending_review` / `completed` / `cancelled`, each arm carrying only its own data) validated at the read boundary with a strongly consistent read. Steps advance only through typed transitions (`enterReview` / `advanceCursor` / `complete`), each a schema-validated whole-row conditional put on the prior state. A missing, unparseable, wrong-state or completed saga yields an `unavailable` result: the handler renders "This request is no longer active", or re-renders the completed embed for an already-completed saga.

## Cross-Cutting Patterns

- **Repository pattern**: `DynamoTableAccess` (`src/storage/repositories/base.ts`) is the shared abstract base most typed backends (`ContactBackend`, `SessionJournalBackend`, `AllowlistSagaBackend`, `OutboxBackend`, ...) extend for common get/put/query/scan primitives; a backend with a specialized need (a strongly-consistent conditional put, a custom paginated query) sends its own SDK command directly alongside the inherited ones rather than bending the base to fit. Some storage classes bypass the base entirely: `PersonAllowlist` and `MemoryToolBackendCore` manage their own DynamoDB client access, and the contacts and memory-tool reconciliation functions are plain functions, not backend classes, issuing raw commands. There is no ad-hoc SDK access outside `src/storage/` and `src/services/`.
- **Dependency injection**: subsystems receive their dependencies as constructor arguments or factory parameters, never via module-level singletons, with one process-scoped exception: `src/storage/dynamo-retry.ts`'s module-level health notifier, installed by `src/index.ts` at startup and cleared on shutdown, so every DynamoDB call site can report a network-classified failure without threading a health registry through `withDynamoTimeout`.
- **Zod schemas**: all external data (config, DynamoDB records, MCP tool arguments, API responses) is validated at the boundary with Zod before entering typed TypeScript.
- **Branded types and channel scopes**: `MemoryPath`, `LayerName`, `ChannelId`, `GuildId`, `UserId` and others prevent mixing identifiers of different kinds. Discord's `types.ts` also defines `ChannelScope`: either a numeric `GuildId` or the fixed `DM_SCOPE` sentinel, so direct messages cannot masquerade as guilds. Factory functions (`createLayerName()`, `createContentType()`) and type guards (`isLayerName()`, `isContentType()`) replace unsafe `as` casts with runtime-validated construction.
- **Class-based components**: `AnswerClassifier`, `StreamTracker`, `QuestionRegistry`, `DiscordRateLimiter`, `PresenceManager`, `MessageCoordinator` are proper TypeScript classes with private fields.
- **Retry with exponential backoff**: `src/utils/retry/` supplies the `RetryPolicy` type, error classifiers, and the `retryAsync` / `retryAsyncGenerator` wrappers. `retryAsync` is used for Discord and Bluesky calls; the conductor implements its own retry loop over the same policy and classification types for Claude; DynamoDB relies on the AWS SDK's `maxAttempts` plus `withDynamoTimeout`.
- **Structured logging**: `@hughescr/logger` provides structured, leveled log entries with per-call context fields (e.g. `taskId`, `sessionId`, `personId`); there is no dedicated correlation/request ID threaded across subsystem boundaries — log correlation across a turn relies on the fields each call site chooses to include.
- **`assertNever()`**: exhaustiveness helper for discriminated union switches that throws `InvariantViolationError` at runtime if an unhandled variant slips through.
- **Lost-task recovery from the journal**: crash recovery (`src/agent/session/recovery.ts`) reads a role's session journal window at boot to find background tasks that never reached a terminal state, reporting them as lost rather than silently forgetting them — see "Session journal" above.
- **Activity auto-logging**: `ActivityLogger` records cross-platform interactions automatically for cross-platform context awareness.

## Configuration and Errors

`src/config/` loads all configuration from environment variables using the `env-var` package for type coercion, validated by Zod schemas at startup. `config/retry-config.ts` holds the Claude retry policy, validated with utils' `retryPolicySchema`, and `src/app/sessions.ts` reads it; utils does not import config.

`src/errors/` defines `IsambardError` as the base class for all application errors. It carries a typed `code: ErrorCode` field and a context bag for structured diagnostics. The subtrees are: `StorageError` (DynamoDB, memory tool, contacts, vector index, reconciliation errors), `DiscordError` (channel registry, presence, permission errors), `EmailError` (WildDuck, classifier, processing errors), `BskyError` (AT Protocol auth, rate limit, validation errors), `CaldavError` (calendar auth, fetch, timeout, ambiguous-match errors), and `BrowserError` (navigation timeout errors). `MediaProcessingError`, `ConfigValidationError`, and `MemoryVecError` (embedding library errors) extend `IsambardError` directly as cross-cutting exceptions. A separate `PathSecurityError` handles file path validation failures. All error codes are centralized in `ErrorCode` enum in `errors/codes.ts`.

## Session Architecture

There is no mode flag: the long-lived, journaled conversation conductor described above is the only path — `SESSION_MODE` and `session.mode` were removed from `sessionConfigSchema` (P13b) once production soaked cleanly, along with the one-shot `handleInput`-per-message agent, the perch and catch-up session runners, and their tests. `src/index.ts` unconditionally *builds* (but never opens) the conductor, hands it to `createDiscordBot` and to the session supervisor (`src/app/runtime.ts`); the supervisor is what actually calls `open()`, once the bot's first `clientReady` has signalled that the guild cache and channel registry exist. A conversation open that rejects or outlasts `CONDUCTOR_OPEN_TIMEOUT_MS` exits the process with code 1 (the deploy supervisor restarts it); a perch open failure leaves perch disabled with no restart. `open()` pushes a `shouldQuery:false` `[BOOT]` handshake envelope (the boot bundle `buildBootBundle` builds for that attempt when it is non-empty, otherwise a bare open/resume marker — see "Boot re-seed by kind" below; an in-process reopen — a crash reopen or a requested one — pushes a reopen handshake that tells the model, in plain words, why the session process was replaced, that this was not an offline gap, and, when there were any, which background tasks the old session process was running and so may never report back — snapshotted synchronously where the reopen starts, before the old handle is closed) onto the new session's queue before it awaits any frame: with a streaming-input prompt the SDK CLI emits nothing — not even the `system/init` frame that carries the session id — until it has read its first user message, so a silent open would never resolve (found on the first production start, 2026-09-06; the handshake yields `init` plus a bare `result` with no model turn). A perch conductor is built the same way, but only when `config.perch?.enabled` is also set — an unconfigured or disabled perch is not built at all, so a default deployment with no perch config runs the conversation conductor alone. SDK transcript files are retained indefinitely now that sessions are long-lived; there is no startup retention sweep. Rollback for this package (and any change to `src/index.ts`, `src/config/schemas.ts`/`loader.ts`, or the deleted one-shot files) is a branch reset to the previous tag plus `bun run deploy:running` — there is no env var to flip back.

**A turn a crash cuts off** (#99): a crash reopen re-queues the interrupted turn only when the host pushed it itself (`beginTurn` stamped its wire uuid), so a submitted turn is re-sent to the replacement session exactly as before. A turn the SDK started on its own — an adopted background-task wake or an adopted peer message — is never re-sent, because the model already read its input: `handleMidLifeClosed` settles it at crash time, before any reopen attempt, as a failed turn (journaled `turn_failed`; wake delivery sends nothing for a reply-less result), and the reopen handshake gets one extra paragraph naming it as cut off — pointing at the transcript when the reopen resumes, quoting the input when it falls back to a fresh transcript that never saw it. A bare spontaneous notification turn is simply dropped. `session_opened` now clears the ledger's `turn` as well as its tasks, so a turn the dead process left open never reads as busy in the new one.

**A turn shutdown cuts off** (#120): `Conductor.shutdown()` settles any turn still running when it closes the session handle — on the real SDK the interrupt is acknowledged but the close lands before the turn's result frame (#41 Part A, case A6), and on the hard-deadline path no interrupt may have been sent at all. The caller gets `interrupted`, never a reply, with the source that first asked for the interrupt or `'shutdown'`; the journal gets the same reply-less `turn_completed` row an in-time interrupt writes. The Discord path treats it as any interrupted turn, an adopted wake's delivery sends nothing, and a bare spontaneous turn is dropped. Boot recovery (`computeRecovery`) lists only turns that produced a reply as undelivered, so a reply-less `turn_completed` — interrupted, shutdown-settled or a non-success result — is never shown in the boot bundle as an undelivered response, nor redelivered (#130). The turn's escalation timer and shutdown's own turn-wait timer are cleared, so none outlives the conductor, and once closed the conductor ignores every frame the old handle still forwards, so a late assistant frame or result can neither open a turn, consume a pending wake/peer adoption, nor settle anything.

**Boot re-seed by kind** (R1, #62, #98): `src/agent/session/boot-bundle.ts`'s `createBootBundleBuilder` renders a different section set for each of four `BootKind`s — no kind repeats context already in the transcript, and no kind drops context that was never shown. Delivery is split (#98), because the real Claude Agent SDK never invokes an SDK-callback `SessionStart` hook for `startup` or `resume` in a streaming-input `query()` session (anthropics/claude-agent-sdk-typescript#465; probed on 0.3.258, 0.3.273 and 0.3.280), though it does for `compact`, and it reliably delivers the first streamed message:

- `fresh` and `restart_resume` ride in the conductor's opening `[BOOT]` handshake. `createConductor`'s `buildBootBundle` callback (wired per role in `src/app/sessions.ts`) is called once per open attempt, just before that attempt's query exists: `restart_resume`/`boot` before a boot open resumes its stored session, `fresh`/`boot` before a fresh boot open or the fresh fallback after that resume failed (so a new transcript never gets a resume-only bundle), and `fresh` with the reopen's cause before an in-process reopen's fresh fallback. A reopen that resumes builds nothing.
- `compact` is `additionalContext` on the SessionStart callback (`src/agent/hooks/boot-bundle.ts`). A `startup`/`resume` firing of that callback is a logged tripwire (`SessionStart <source> callback fired: upstream claude-agent-sdk-typescript#465 appears fixed…`) that adds nothing, so an upstream fix cannot deliver the bundle twice; the log line is the cue to re-evaluate.
- The build is bounded by `BOOT_BUNDLE_BUILD_TIMEOUT_MS` (10 s, on the injected clock). That caps the delay the build adds to one open attempt; it does not guarantee the whole `open()` fits inside the session supervisor's 30 s `CONDUCTOR_OPEN_TIMEOUT_MS` (`src/app/runtime.ts`). On a rejection or timeout the conductor asks `renderBootBundleFallback` for a synchronous recovery-only bundle (perch wires `formatRecoveryOnlyBootBundle`, because by then the conductor has journaled the lost tasks as `task_lost` and no later read will report them; conversation wires none, since its catch-up envelope owns lost tasks), else pushes the bare marker. The build runs outside boot recovery's try/catch, so a builder failure can never reset the recovery-seeded delivery guard. If `shutdown()` begins during the build, `open()` rejects without spawning a query, and a boot handle that settles after shutdown began is closed rather than left running.
- An in-process reopen's fresh fallback appends its bundle as the last paragraph of the #62 reopen handshake, whose continuity sentence says "Your working memory is re-seeded below." when there is a bundle and "earlier context from it is not available to you" when there is none.

| Kind | When | Conversation role injects | Perch role injects |
|---|---|---|---|
| `fresh` | cold process start | current focus/state, events (since `eventsSinceMs` when given, else the rolling `bootEventsWindowMs` window), task list, channel list, recently-talked-to users, active tasks — no lost tasks or undelivered envelopes, which are the merged Discord boot envelope's exclusive responsibility (see below), so a restart never shows the same recovery content in both places | task list, the full `buildPerchContext` block, lost tasks, undelivered envelopes |
| `compact` | working memory was just reset by a `/compact` | current focus/state, events since the mark, task list, active tasks — no channel list, recent users, lost tasks, or undelivered envelopes, because nothing was lost across a compaction (Discord turns are held by the conductor for its duration) | same sections as `fresh` |
| `restart_resume` | process restart, transcript survived | only the live active-task set (from the ledger) — no state, task list or channels, since none of that was lost, and no events/lost-tasks/undelivered either (again the merged Discord boot envelope's exclusive job); `build()` returns `''` once even the active-task list is empty, which is the normal case at boot (the ledger is new), so the handshake is the bare `[BOOT] Session resumed` marker and nothing is fetched | lost tasks, undelivered (the conductor's own recovery read, so no extra journal read), active tasks only, else `''` |
| `reopen` | in-process reopen (crash reopen or requested reopen, e.g. an identity change), transcript survived | nothing: the conductor never builds a bundle for a reopen that resumes, so only the #62 reopen handshake is pushed (the builder's `''` early return for this kind stays as a guard) | nothing, and no journal read |

A reopen whose resume fails falls back to a fresh session and builds a `fresh` bundle with the reopen's cause and empty recovery lists: it gets the full re-seed, minus the old session's active tasks (conversation, via `coveredByReopenHandshake` in `src/app/sessions.ts`) and journal recovery (perch), which the reopen handshake already covers. The build happens before the replacement's `finishOpen` clears the ledger, which is why the suppression keys on the cause, not the ledger.

**No bundle of any kind carries identity** (WP4a): identity is deliberately absent from every boot bundle — `boot-bundle.ts` has no `## Identity` section, no `IdentitySource` and no `identityCache` read. It lives in the SDK `systemPrompt` instead (`src/agent/prompts/system-prompt.ts` appends the `## Identity` section; `src/app/sessions.ts` builds the string and `buildOptions` reads that variable at every open and reopen), which the SDK fixes at `query()` time. So an identity-layer memory write invalidates `IdentityCache`, `sessions.ts` rebuilds the session prompt and the sub-agent prompt (`src/agent/prompts/subagent-prompt.ts`) from one identity read, and — only when the rendered prompt actually changed — calls `Conductor.requestReopen` (`src/agent/session/conductor.ts`) for a controlled close-and-resume that installs it: the conversation role reopens at the next idle point, the perch role defers to the end of the current slot. Either way, the reopen then waits for the old session's background work, because closing the session process would kill it (#97). It waits until no background task (of any ledger kind, monitors included) is running, no SDK-started wake or peer turn is still pending adoption, and no task has finished within the last `REOPEN_WAKE_SETTLE_MS` (5 s, a best-effort allowance for the SDK's wake to arrive). The wait is bounded by `session.reopenTaskWaitMs` (default 2 minutes, env `SESSION_REOPEN_TASK_WAIT_MS`), measured from the first request still pending; a later request keeps that deadline. No queued turn starts during the wait. When the bound runs out, the reopen goes ahead: the #62 handshake lists the tasks still running, and a warning is logged for any result that may not have been delivered. Shutdown cancels the wait. A crash during it reopens at once, and that reopen satisfies the request.

On the Discord side, the boot bundle and the inbox catch-up no longer inject as two separate messages: `runConductorInboxInit` (`src/integrations/discord/setup/catchup-setup.ts`, reached through the bot's recovery adapter when the session supervisor runs boot recovery — the supervisor owns the journal read, `computeRecovery`/`lastKnownAt` and the `runBootSequence` call, handed to the adapter as a `BootRecoveryRuntime`) builds and submits ONE merged boot envelope once the crash-recovery/replay sequence resolves — the unread overview, events since a journal-derived boundary (`src/agent/session/recovery.ts`'s `lastKnownAt`, the max `at` over the conversation journal's `turn_completed`/`turn_failed` entries — deliberately NOT `turn_submitted`, which has no corresponding `JournalEntry` variant and, even if it did, a submission alone would not establish that Izzy actually saw or processed anything — falling back to `bootEventsWindowMs` when the journal has none), the recovery's lost tasks (sourced from a pre-`conductor.open()` snapshot — see `ConversationConductorResult.bootLostTasks` — so it cannot race `Conductor.open()`'s own `task_lost` journal write), and the undelivered replies this same boot actually redelivered. `ContextPolicy`'s events mark is seeded from that same boundary BEFORE `runBootSequence` opens the ingress gate (not from inside the merged-envelope builder itself, which runs after), so a live turn released by that gate can never race the seed against a stale mark. The merged envelope submits through a turn (a `QueryEnvelope`, sent `shouldQuery: true`) when it carries unread mail or a lost task, or is appended without opening one (an `AccumulationEnvelope` via `Conductor.appendWithoutTurn`) when it carries only an events/redelivered summary that does not need a reply — and submits nothing at all when there is genuinely nothing to report.

**Compaction lifecycle** (#73): the conductor is the sole dispatcher of the `compaction_started`/`compaction_completed`/`compaction_failed` ledger events, and `Ledger.compaction` is the single "compacting" authority (there is no compacting `ActivityPhase`; presence renders one `compacting` marker from the ledger flag). A compaction starts when `CompactionGuard` submits `/compact` or the PreCompact hook calls `Conductor.compactionStarted`, and completes when the conductor observes its own `compact_boundary` frame or the PostCompact hook calls `Conductor.compactionCompleted` — whichever arrives first; every reducer is idempotent, so the second observation notifies nobody and the journal records one `compaction_completed`.

**Compaction threshold and its tuning** (Q4, Q11): `session.compactThresholdPercent` (`SESSION_COMPACT_THRESHOLD_PERCENT` env var, default 60) is the context-window usage percentage at which `CompactionGuard` (`src/agent/session/compaction-guard.ts`) submits a `/compact`. It is a live value — `CompactionGuard.setThresholdPercent`/`getThresholdPercent`, exposed on `Conductor` as `setCompactionThresholdPercent`/`getCompactionThresholdPercent` — rather than a value fixed at session construction. `src/agent/session/compaction-tuner.ts`'s `createCompactionThresholdTuner` (wired into both `createConversationConductor` and `createPerchConductor` in `src/app/sessions.ts`) subscribes to each role's `LedgerStore` and nudges this live threshold toward a configured target inter-compaction interval, derived from Q4's `CompactionTelemetry` (`compaction-telemetry.ts`) records: consecutive *finished* records' `startedAt` deltas give the observed intervals, recomputed on every `compaction_completed` ledger event, and only the most recent `INTERVAL_HISTORY_WINDOW` (5) of them are ever considered, so a long-past burst of frequent compactions cannot keep the threshold pinned at a band edge once conditions settle. Three independently-optional env vars configure the tuner's band, all read in `src/config/loader.ts`'s `session` block alongside `SESSION_COMPACT_THRESHOLD_PERCENT`: `SESSION_COMPACT_THRESHOLD_MIN_PERCENT` and `SESSION_COMPACT_THRESHOLD_MAX_PERCENT` (each an integer 1-100, clamping the tuned value; a missing bound defaults to `compactThresholdPercent` itself) and `SESSION_COMPACT_TARGET_INTERVAL_MS` (a positive integer; missing means `Infinity`, which `computeTunedThreshold` treats as an explicit no-op step — never a step in either direction, regardless of how wide the min/max band is — rather than letting every observed interval vacuously count as "shorter than target"). With none of the three set, `min === max === compactThresholdPercent`, so the tuner's clamp always returns that single value regardless of observed intervals — deployed behaviour is unchanged with no new env vars, and rollback is unsetting them.

**Memory-tuned envelope sections vs. the perch full block** (Q9, Q12, R1): every Discord conductor turn runs through `ContextPolicy` (`src/agent/session/context-policy.ts`), which gates five envelope sections so each carries only what changed since it was last shown, not the whole thing every turn — the per-user `[About this user]` memory block (`shouldInjectUserMemory`/`markInjected`, R1), new memory events (`eventsDelta`/`markEventsSeen`), the state top-set (`stateTopSetDelta`/`markStateTopSetSeen`, Q9), the day's calendar agenda (`calendarDelta`/`markCalendarSeen`, Q12 — polled at most once an hour or on a local-day rollover, per-user, via `loadCalendarAgenda`), and service health (`healthNote`/`markHealthSeen`, Q12 — fed by an optional `healthRegistry`, rendered only on a state transition, including the return to all-online). The per-user memory gate is fingerprint-based rather than time-windowed (R1, replacing the old fixed-hours re-injection clock and its config field): `conductor-processor.ts` loads the block fresh on every message (one query, same as the one-shot path always did) and injects it only when its content hash differs from the fingerprint recorded at that user's last `markInjected` call — an unchanged block is never re-injected no matter how long it has been, and a changed block re-injects immediately with no elapsed time required. `src/integrations/discord/setup/conductor-processor.ts` wires all five into `buildDiscordEnvelope`'s `userMemoryBlock`/`newEvents`/`stateChanged`/`calendarChanged`/`healthNote` params and marks each seen only after a non-withdrawn `submit()` — a withdrawn (debounce-interrupted) turn never showed its envelope to Claude, so marking it would wrongly skip the real injection next time; the one exception is the memory fingerprint mark itself, which is written unconditionally on every non-withdrawn turn (not gated on whether the block was actually injected that turn), since the mark always reflects the block just loaded and re-recording an unchanged fingerprint is a no-op. `ContextPolicy.resetAll()` (called by the compaction sink once a `/compact` completes) clears every user's memory fingerprint, the state top-set baseline, the calendar poll cache, and the health mark — re-arming all four as if this were a cold start — but deliberately NOT the events mark: a compaction can run for minutes with perch active in parallel, and events written during that window must still reach the next `eventsDelta`/`eventsSinceMs` read rather than falling through a reset boundary. A `calendarDelta()` rejection (a transient CalDAV failure) is logged and swallowed rather than failing the turn: the envelope still goes out, just without a `[Calendar]` section that turn. Perch is deliberately exempt from all of this: `createPerchConductor` (`src/app/sessions.ts`) builds no `ContextPolicy` at all, and perch turns instead carry the FULL context every time via `buildPerchContext` (full agenda, full service health, top-3 state — `agent/perch/envelope.ts`'s `buildPerchSlotEnvelope` renders it verbatim, with no `calendarChanged`/`stateChanged`/`healthNote` parameters to plumb a delta through even if one existed). This is the right tradeoff for a session that runs only a handful of turns per day — each one needs to be self-contained — rather than a gap to close later.

**Background-work wake turns** (R2): launching a sub-agent, workflow, or backgrounded `Bash` fires PostToolUse inside the launching turn, and `createTaskLaunchHooks` (`src/agent/hooks/task-launch.ts`) records the launch — `taskId`/`toolUseId`, plus the launching turn's `kind`/`channelId`/`authorId` from `Conductor.status().turn` — into `TaskLaunchRegistry` (`src/agent/session/task-launch-registry.ts`, journaled as `task_launched` and seeded from that journal at boot). When the work finishes, the SDK does not resume the launching turn; instead it delivers a `<task-notification>` UserPromptSubmit wake and starts a fresh spontaneous assistant turn. That hook calls `Conductor.adoptWakeTurn`, which looks the launch up in the registry, synthesizes a `task`-kind `Envelope` carrying the launching turn's channel/author, and opens a real turn around it (journaling `turn_submitted`/`envelope_submitted` like `beginTurn`, but without re-pushing to the SDK queue, since the SDK already started this turn) — so whatever Izzy writes is journaled and delivered exactly like an ordinary reply, not dropped as a bare `notification` turn with no envelope. Delivery is `createWakeTurnDelivery` (`src/integrations/discord/setup/wake-delivery.ts`, wired via each role's `setWakeTurnDelivery` in `src/app/sessions.ts` and called from `bot.ts`'s `clientReady`, before it signals readiness): a `task` envelope with a known channel (its own `channelId`, or a well-known kind such as `perch`) delivers there via `Conductor.deliver`; one whose launch record was evicted or never found — and every `notification`-kind reply from `NotificationBridge.attachReplyDelivery` (host-submitted email/outage notifications, which never carry a channel) — routes to the `fallback` well-known channel instead of being silently discarded, prefixed to say so. Real-SDK facts (probe `probe-task-wake.ts`, SDK 0.3.258): the wake's `<task-notification>` prompt carries `<task-id>`/`<tool-use-id>` matching the launching PostToolUse's ids, and fires as a UserPromptSubmit hook *before* the woken turn's first ROOT assistant frame. A child assistant frame has a non-null `parent_tool_use_id` and can arrive while the root is idle immediately before that hook; the conductor and ledger keep it observable but do not let it open or adopt the root turn. A subagent-internal task notification (`output_file: ''`, no `tool_use_id` correlation) never fires the hook and is ignored.

**Session peers** (`docs/plans/session-peers-and-quota.md`): the conversation and perch sessions are two independent Claude Code processes, and each registers in the machine-wide peer registry that `ListAgents`/`SendMessage` read and address, under the titles `Izzy-main` and `Izzy-perch` (`SESSION_PEER_NAMES` in `src/agent/session/query-options.ts`, set via the `CLAUDE_CODE_SESSION_NAME` env var — `Options.title` alone does not reach the registry). A `SendMessage` from one to the other arrives as the SDK's raw `<cross-session-message>`-wrapped `UserPromptSubmit` prompt; `src/agent/hooks/peer-message.ts`'s hook parses it and calls `Conductor.adoptPeerTurn` (`src/agent/session/conductor.ts`), which adopts the turn the SDK already started. `buildPeerEnvelope` (`src/agent/session/envelope.ts`) renders a host-only `[PEER · <fromName> · stamp]` journal/ledger record; the model sees the raw wrapper plus the hook's `additionalContext`, which says an idle peer turn has no automatic outbound delivery and uses `SendMessage` only when a peer reply is needed. A peer result must be delivered to Discord when it completes a follow-up this session already owes or promised, or the peer explicitly requests delivery; origin metadata alone creates no duty to contact the user. `src/agent/prompts/system-prompt.ts`'s `buildPeerPrompt` teaches each role its own name, its other half's name, and the rule that any registry entry without the `Izzy-` prefix is most likely one of Craig's own Claude Code sessions rather than a peer. That prefix is enforced, not just documented: `src/agent/hooks/agent-naming.ts`'s `PreToolUse` hook stamps `Izzy-` onto every `Agent` launch's `name` and rewrites a `Workflow` script's `meta.name` literal the same way, so a sub-agent or workflow either session launches also reads as Izzy's in the registry. A known gap: a peer message that arrives while the receiver is already mid-turn is folded into that turn by the SDK with no `UserPromptSubmit` hook firing at all, so it never reaches the ledger or journal as its own `peer` turn; that active turn retains its existing reply route. If that route matches an owed or explicitly requested user follow-up it carries the final response; a different or absent route requires explicit `sendDiscordMessage`, while a peer reply still uses a separate `SendMessage` when needed (see the probe's P3 in the plan doc).

**Quota awareness**: both sessions see the shared Claude Max subscription's utilization on every turn. The SDK emits a `rate_limit_event` frame whenever its rate-limit headers change; `src/agent/session/ledger.ts` normalises those five-hour and weekly windows into `Ledger.quota` (`source: 'headers'`). `src/app/quota-poller.ts` owns the shared polling lifecycle and ledger dispatch; `src/integrations/utraque/provider-capacity.ts` parses schema-2 reports for Codex and DeepSeek quota, balances, local usage history, and models.dev reference prices. `src/integrations/anthropic/usage-fallback.ts` parses the separate direct OAuth fallback when permitted. Neutral snapshot types and fresh Anthropic quota projection stay in `src/agent/session/provider-snapshot.ts`; neither integration owns timers or ledger fan-out. In the configured SDK-only Anthropic mode it omits the Claude bearer, ignores the deliberately unrequested Anthropic quota row, and never dispatches that row into the ledgers. `src/agent/session/ambient-lines.ts` renders a provider-keyed `Quota:` JSON block. When trustworthy local history and matching reference prices exist, a quota bucket includes a rough token estimate normalized to the cheapest eligible routed model with the same observed input/output/cache mix; DeepSeek balance estimates stay per model. The sample periods, token categories, local-only coverage, calculated API-reference cost basis, and price timestamp remain visible so these planning estimates are not mistaken for subscription calibration. `createSessionAmbience` in `src/app/sessions.ts` appends the block to every time-header producer. `src/agent/session/quota-notes.ts` still watches the SDK ledger values and calls the notification bridge, always `wake: false`, when a window's peak crosses a configured threshold or resets; its `isPaused()` remains the perch quota ceiling used by the scheduler and presence marker.
